## 1. 개요

### 1.1 한 줄 정의

**Live Player는 흩어져 있는 6종의 영상 소스를 하나의 라이브러리로 묶어 자동·수동으로 편성하고, 그 편성을 무결절로 재생해 OBS·vMix 또는 모니터로 내보내는 다채널 플레이아웃 도구다.**

출력 대상은 채널마다 선택하며, **한 채널이 여러 출력을 동시에 가질 수 있습니다.**

| 출력 방식 | 최종 목적지 | 주 용도 |
|---|---|---|
| **스위처 공급** — 창 캡처 / NDI | OBS·vMix → 유튜브 라이브 등 | 방송 송출 |
| **모니터 직출력** | 연결된 모니터 = 최종 화면 | 행사장·현장 모니터, 다중 화면 |

둘은 배타적이지 않습니다. 같은 채널을 OBS로 보내면서 동시에 현장 모니터 3대에 띄울 수 있습니다.

### 1.2 배경 / 문제 정의

유튜브 라이브 채널이나 모니터 송출을 운영할 때, 실제로는 콘텐츠가 여러 곳에 흩어져 있습니다.

- 로컬 하드의 완성본 영상 파일
- 계속 파일이 쌓이는 작업 폴더
- 이미 자기 유튜브 채널에 올려둔 영상과 재생목록
- Cloudflare Stream에 올려둔 영상
- Bunny Stream에 올려둔 영상

지금은 이걸 편성하려면 OBS 미디어 소스를 하나씩 손으로 바꾸거나, 로컬로 전부 내려받아 재인코딩해야 합니다. 24시간 채널이나 장시간 송출은 사실상 사람이 붙어 있어야 하고, **채널을 하나 늘리면 운영 부담이 그대로 두 배가 됩니다.**

**문제의 핵심은 "소스가 여러 곳이라 하나의 편성표로 묶이지 않는다"는 것입니다.**

### 1.3 목표

1. 6종 소스를 **출처와 무관하게 동일하게 다루는 단일 라이브러리**를 제공한다.
2. 시간 블록을 지정하면 **길이를 계산해 자동으로 채우는 편성**과, 순서를 직접 짜는 **수동 편성**을 모두 지원한다.
3. 편성된 내용을 **검은 화면 없이 이어 재생하는 출력창**을 띄운다.
4. **여러 채널을 동시에** 독립 편성·독립 출력한다.
5. 채널마다 **출력 대상을 선택**한다 — OBS·vMix로 공급하거나, 연결된 **모니터에 직접 송출**하거나, 둘 다 한다.
6. 한 채널을 **여러 모니터에 동시 출력**한다. 모니터마다 해상도·스케일 모드를 따로 맞춘다.
7. **무인 24시간 운영**이 가능하도록 실패 시 자동 복구한다.

### 1.4 비목표 (Non-goals)

명시적으로 이번 범위에서 제외합니다.

- **영상 인코딩·트랜스코딩** — 인코딩은 OBS/vMix가 담당. Live Player는 재생과 편성만 한다.
- **직접 RTMP 송출** — 스트리밍 출력은 OBS/vMix에 위임한다. 자체 송출 기능을 만들지 않는다.
- **4K 출력** — 전면 보류(2026-08-27). 개발·검증·권장 구성 전부 1080p 기준으로 진행한다. 보류 배경과 재개 시 확인 사항은 §3.7에 기록.
- **시청자 전송(딜리버리) 인프라** — 자체 HLS 서버·CDN 운영은 Live Player 뒤에 붙는 **별도 컴포넌트**이며 이 제품에 포함하지 않는다. 다만 어떤 전송 구조를 택하느냐가 이 제품의 소스 설계를 좌우하므로, 검토 결과를 **부록 C**에 결정 기록으로 남긴다.
- **영상 편집** — 컷 편집, 자막 렌더링, 합성은 다루지 않는다.
- **타인 콘텐츠 재송출** — 본인 소유 채널·계정의 콘텐츠만 등록 대상으로 한다 (§6.1 참조).
- **디지털 사이니지** — 전광판·매장 TV 편성은 기존 CDMB CMS의 영역이며, 여기서 중복 구현하지 않는다.
- **멀티테넌트 SaaS** — 채널은 여러 개지만 **운영자는 한 명**이다. 계정 관리·권한 분리·요금제는 다루지 않는다.

### 1.5 CDMB CMS와의 관계

같은 "영상 + 스케줄 + 재생창" 구조지만 **출력을 누가 받느냐**가 달라서 별개 제품입니다.

| | CDMB CMS | Live Player |
|---|---|---|
| 출력의 최종 소비자 | 디스플레이(전광판·TV) = 종점 | **선택** — OBS/vMix(중간 단계) 또는 모니터(종점), 또는 동시에 |
| 재생창의 성격 | 최종 화면 | **스위처 입력 소스 또는 최종 화면** |
| 전환 시 검은 프레임 | 문제되지 않음 | **방송사고** |
| 스케줄 모델 | 요일 × 시간대 그리드(반복 편성) | 런다운(연속 편성, 예상 시작시각) |
| 항목 길이 정보 | 없어도 동작 | **필수** (자동 편성의 전제) |
| 외부 제어 | 서버 → 플레이어 단방향 | 스위처와 **양방향** 상태 동기화 |
| 동시 출력 | 디스플레이 여러 대에 **같은 편성** | 채널마다 **다른 편성** |
| 소스 종류 | 로컬 파일·업로드·유튜브·이미지 | 로컬·폴더·유튜브(채널)·CF Stream·Bunny |
| 배포 형태 | 멀티테넌트 SaaS + 로컬 앱 | 단일 운영자용 로컬 앱 |

#### 모니터 직출력 도입에 따른 경계 재정의

모니터 직출력이 추가되면서 두 제품이 겹치는 영역이 생겼으므로 경계를 다시 긋습니다.

Live Player의 모니터 출력은 **같은 PC에 연결된 로컬 모니터**만 대상으로 하며, 목적은 "방송용으로 편성한 콘텐츠를 현장 화면에도 함께 띄우는 것"입니다. 다음은 여전히 CMS의 영역이며 Live Player에서 구현하지 않습니다.

- **원격지 디스플레이의 관리·모니터링·패치** (Remote Manager, 안드로이드 플레이어, 클라우드 페어링)
- **다수 현장·회원사 단위 운영**, 라이선스·요금제·권한 분리
- **사이니지 고유 기능** — 밝기 주야 제어, 포스터·현수막 우선 송출, 자막 티커·시계·날씨 위젯, 멀티존 레이아웃, 취침 스케줄

> **한 줄 요약**: 화면을 *관리*하는 게 목적이면 CMS, 편성을 *방송*하는 게 목적이면 Live Player. 모니터 출력은 후자의 부가 출력 경로일 뿐 사이니지 운영 기능이 아니다.

**코드는 공유하지 않되, 검증된 설계 원칙은 가져옵니다.**

가져올 개념
- 서버가 진실의 원천(single source of truth), WebSocket 브로드캐스트로 상태 전파
- 미리보기와 실제 출력이 **같은 재생 엔진**을 사용 → 화면 일치 보장
- JSON 파일 스토어 기반의 가벼운 영속성
- Electron 멀티모니터 감지·전체화면 처리
- **스케일 모드** (1:1 무왜곡 / 여백맞춤 / 꽉채움 / 늘림) — 모니터 직출력에 그대로 필요

새로 만들 것
- A/B 무결절 재생 엔진
- 런다운형 스케줄 모델
- 소스 어댑터 레이어
- **채널 관리 계층** (독립 편성·독립 출력·독립 오디오)
- OBS·vMix 연동 계층

## 2. 사용자

### 2.1 타깃 사용자

| 유형 | 특징 | 핵심 니즈 |
|------|------|-----------|
| **다채널 운영자** | 유튜브 24시간 라이브를 주제별로 2~4개 채널 운영 | 채널마다 다른 편성이 사람 없이 동시에 돌아가야 함 |
| **1인 채널 운영자** | 유튜브 24시간 라이브(음악·설교·강의 재방송)를 혼자 운영 | 한 번 편성해두면 사람 없이 계속 돌아가야 함 |
| **교회·단체 미디어 담당** | 주중 재방송 채널 + 주일 라이브. OBS는 이미 사용 중 | 기존 OBS 워크플로를 바꾸지 않고 소스만 자동화 |
| **행사·전시 운영자** | 현장 모니터 여러 대. 같은 영상을 여러 화면에, 또는 화면마다 다른 영상 | **OBS 없이 모니터로 바로 송출**, 모니터별 해상도·비율 대응, 고정 시각 정확도 |

**공통 전제**: OBS 또는 vMix를 이미 쓰고 있으며, 그것을 대체할 생각이 없다.

### 2.2 사용 시나리오

**S1. 24시간 재방송 채널 (자동 편성)**
1. 운영자가 자기 유튜브 채널의 "지난 설교" 재생목록을 라이브러리에 연결한다.
2. 채널 1을 만들고 "매일 00:00~24:00, 이 재생목록을 랜덤 순서로 채움"으로 자동 편성한다.
3. 채널 1 출력창을 띄우고 OBS에서 캡처해 유튜브 라이브를 시작한다.
4. 이후 사람이 개입하지 않아도 매일 편성이 재생성되어 계속 나간다.

**S2. 다채널 동시 운영**
1. 채널 1은 "설교 재방송", 채널 2는 "찬양 음악", 채널 3은 "행사 모니터"로 각각 만든다.
2. 채널마다 해상도·오디오 출력 장치·편성이 다르다.
3. 세 개의 출력창이 동시에 각자의 런다운을 재생한다.
4. 하나가 장애로 재기동돼도 나머지 두 채널은 영향받지 않는다.

**S3. 정시 콘텐츠가 있는 편성 (수동 + 고정시각)**
1. 로컬 폴더의 영상들로 오전 블록을 자동으로 채운다.
2. "10:00 정각에 반드시 이 영상"을 **고정 시각 항목**으로 지정한다.
3. 앞 항목이 10:00을 넘기면 자동으로 트림하거나, 모자라면 필러를 넣어 정시를 맞춘다.

**S4. 현장 대응 (수동 개입)**
1. 송출 중 운영자가 특정 채널에서 "다음 항목 건너뛰기"를 누른다 → 현재 항목이 끝나는 즉시 다음으로 넘어간다.
2. "지금 바로 이 영상"을 누르면 현재 항목을 끊고 즉시 전환한다.
3. 개입이 끝나면 원래 런다운으로 자동 복귀한다. **다른 채널은 영향 없다.**

**S5. 스위처 연동**
1. 채널별로 OBS WebSocket 접속 정보를 등록한다 (같은 OBS의 다른 씬, 또는 서로 다른 OBS 인스턴스).
2. 편성 항목에 "이 항목 재생 시 OBS 씬을 `LIVE-VIDEO`로 전환" 규칙을 건다.
3. 편성이 끝나는 시각에 자동으로 `대기화면` 씬으로 되돌린다.

**S6. 모니터 직출력 (스위처 없이)**
1. 행사장 PC에 모니터 3대가 연결돼 있다.
2. 채널 1의 출력 대상으로 모니터 A·B·C를 모두 선택한다 → 세 화면에 같은 편성이 나간다.
3. 모니터 C만 세로 화면이라 스케일 모드를 "여백맞춤"으로 따로 지정한다.
4. 오디오는 모니터 A에서만 나가도록 하고 나머지는 음소거한다.
5. **OBS를 켜지 않고도** 편성이 그대로 현장 화면에 송출된다.

**S7. 방송 + 현장 동시 출력**
1. 채널 1의 출력 대상에 "창 캡처(OBS용)"와 "모니터 B"를 함께 등록한다.
2. 같은 편성이 유튜브 라이브로 나가면서, 현장 대기실 모니터에도 같은 화면이 뜬다.
3. 오디오는 OBS 쪽 전용 장치로만 보내고 현장 모니터는 음소거한다.

## 3. 핵심 기능

| # | 기능 | 설명 | 우선순위 |
|---|------|------|----------|
| 1 | 소스 어댑터 (6종) | 로컬 파일·폴더·유튜브 영상·유튜브 재생목록·Cloudflare Stream·Bunny Stream을 동일 인터페이스로 로딩 | **P0** |
| 2 | 통합 라이브러리 | 출처 무관 단일 목록. 길이·썸네일·상태 표시, 검색·필터. **전 채널 공유** | **P0** |
| 3 | 채널 관리 | 채널 생성·설정(기준 해상도·편성·스위처 바인딩), 독립 시작/정지 | **P0** |
| 4 | **출력 대상 관리** | 채널당 **여러 출력**. 스위처 공급(창 캡처) / 모니터 직출력 / NDI 중 선택·조합 | **P0** |
| 5 | **모니터 직출력** | 지정 모니터에 전체화면 송출. 모니터별 해상도·스케일 모드 개별 설정 | **P0** |
| 6 | **편성 블록** | 소스 그룹 × 기간 × 요일(복수) × 시간대(복수) 배치. 주간 그리드 (§3.5.1) | **P0** |
| 6b | **자동 채움** | 블록 없는 나머지 전 시간을 버튼 하나로 채워 24시간 완성 (§3.5.2) | **P0** |
| 6c | 런다운 생성·재생성 | 블록+자동채움 → 날짜별 실행 목록. 수동 수정분 보존 (§3.5.3) | **P0** |
| 6d | 런다운 미세 조정 | 드래그 순서 변경 → 시작시각 즉시 재계산. 온에어 중 편집 (§4.3.4) | **P0** |
| 7 | 무결절 재생 엔진 | A/B 더블버퍼 + 프리로드. 전환 시 검은 프레임 0 | **P0** |
| 8 | 출력창 | 출력마다 1개. 프레임리스·고정 해상도·커서 숨김·오버레이 없음 | **P0** |
| 9 | 오디오 라우팅 | 채널별·출력별 장치 지정. 미러 출력 시 하나만 오디오 활성 | **P0** |
| 10 | 미러 출력 동기 보정 | 같은 채널의 여러 출력 간 재생 위치 드리프트 자동 보정 | **P1** |
| 11 | 블록 내 시간 맞춤 | 반복 / 필러 / 잘라내기 — 소스 길이와 시간대가 안 맞을 때 (§3.5.1) | **P1** |
| 12 | 고정 시각 마커 3종 | Hard / Soft / Not Before. 블록 시작에는 Hard 자동 부여 (§3.5.4) | **P1** |
| 13 | 필러 자동 선정 | 로컬 캐시 항목 중 공백 길이에 맞는 것을 자동 선택 | **P1** |
| 14 | 장애 복구 | 로딩 실패 시 즉시 대체, 출력별 워치독 자동 재기동 | **P1** |
| 15 | 운영 콘솔 | 다채널 그리드 뷰. 채널별 ON AIR / NEXT, 진행률, 즉시전환·스킵 | **P1** |
| 15b | 명령 팔레트 · 키보드 | `Cmd+K` 명령 팔레트, 전 기능 키보드 접근 (§4.5) | **P1** |
| 16 | OBS 연동 | WebSocket v5. 채널별 씬 전환·상태 조회·스트리밍 제어 | **P2** |
| 17 | vMix 연동 | HTTP/TCP API. 입력 전환·상태 조회 | **P2** |
| 18 | NDI 출력 | 창 캡처 대신 클린 피드 직접 공급. **조건부** — 채널·출력이 늘어 화면 공간이 부족할 때 | **P2** |
| 19 | 재생 이력 | 채널·출력별로 언제 무엇이 나갔는지 기록·CSV 내보내기 | **P2** |

### 3.1 소스 어댑터 (P0)

모든 소스는 **하나의 공통 항목(Item)으로 정규화**됩니다. 편성기와 재생 엔진은 출처를 모릅니다.

```
Item {
  id           고유 ID
  sourceType   local | folder | youtube | youtube_playlist | cloudflare | bunny
  title        표시 이름
  durationMs   길이 (필수 — 자동 편성의 전제)
  thumbnail    썸네일 URL / 로컬 경로
  playback     재생 방식별 참조
  maxResolution 원본 최대 해상도 (업스케일 경고·향후 판단용)
  isLocal      로컬에서 즉시 재생 가능 여부 (필러 후보 자격)
  mirrorOf     동일 콘텐츠의 다른 소스 ID (CF ↔ Bunny 폴백용)
  status       ready | resolving | error
  lastCheckedAt
}
```

| 소스 | 등록 방법 | 길이(duration) 획득 | 재생 방식 |
|------|-----------|---------------------|-----------|
| **로컬 파일** | 파일 선택 / 드래그앤드롭 | ffprobe | 로컬 서버가 스트리밍(Range 지원) → `<video>` |
| **지정 폴더** | 폴더 지정 후 스캔·감시 | ffprobe (스캔 시 일괄) | 위와 동일 |
| **유튜브 동영상** | 본인 채널 목록에서 선택 | YouTube Data API `contentDetails.duration` | IFrame Player API |
| **유튜브 재생목록** | 본인 채널 재생목록 선택 | 재생목록 항목 일괄 조회 | 항목별 IFrame Player API |
| **Cloudflare Stream** | 계정 연결 후 목록 동기화 | Stream API `duration` | HLS 매니페스트 → hls.js |
| **Bunny Stream** | 라이브러리 연결 후 목록 동기화 | Video API `length` | HLS 플레이리스트 → hls.js |

**폴더 소스는 "동적 풀"입니다.** 개별 항목이 아니라 폴더 자체를 편성에 걸 수 있고, 파일이 추가되면 다음 편성 생성 시 자동 반영됩니다. 유튜브 재생목록도 같은 성격입니다.

**Cloudflare / Bunny 병행 사용** — 둘 다 HLS로 나오므로 재생 경로는 하나(hls.js)로 통합되고, 어댑터만 두 벌입니다. 병행의 실익은 두 가지입니다.

1. 기존에 어디에 올려뒀든 그대로 쓸 수 있다 (이전 작업 불필요)
2. 같은 콘텐츠를 양쪽에 두면 `mirrorOf`로 묶어 **CDN 장애 시 자동 폴백**이 된다

### 3.2 무결절 재생 엔진 (P0)

**이 제품에서 가장 중요한 부분이며, CMS에서 가져올 수 없는 부분입니다.**

동작 원리
1. 출력창은 비디오 레이어를 **두 개(A/B)** 갖는다.
2. 현재 A가 재생 중이면, 다음 항목을 **B에 미리 로드하고 첫 프레임까지 디코드**해 둔다.
3. A의 종료 지점에서 B를 표시하고 A를 숨긴다 → 검은 프레임이 생기지 않는다.
4. 다음 항목을 A에 다시 프리로드한다. 이후 반복.

프리로드 시작 시점은 소스별로 다르게 잡습니다.

| 소스 | 프리로드 시작 | 근거 |
|------|---------------|------|
| 로컬 / 폴더 | 종료 10초 전 | 디스크 읽기, 거의 즉시 |
| Cloudflare / Bunny | 종료 20초 전 | HLS 세그먼트 버퍼 확보 |
| 유튜브 | 종료 30초 전 | 임베드 초기화 + 버퍼링 여유 |

**디코더 예산** — 부하의 단위는 채널이 아니라 **출력**입니다. 출력마다 A/B 두 레이어를 가지므로 최악의 경우 전체 출력 수의 2배가 동시 디코딩됩니다. 다만 B는 프리로드 구간(10~30초)에만 활성이므로 **평시에는 출력당 1개, 전환 직전에만 2개**입니다. 출력별 프리로드 시작 시점을 의도적으로 어긋나게 배치해 동시 피크를 분산시킵니다.

**유튜브의 한계는 설계에 명시합니다.** IFrame 임베드는 앱이 디코딩을 직접 통제하지 못하고, 광고 삽입 여부·버퍼링 타이밍도 통제 밖입니다. 본인 채널 콘텐츠라도 마찬가지입니다. 따라서 유튜브 항목의 무결절 전환은 **최선 노력(best-effort)**이며 완전 보장 대상이 아닙니다.

> **권장 운영 방식**: 온에어가 중요한 채널은 본인 유튜브 콘텐츠를 Cloudflare Stream 또는 Bunny Stream에 미러링해 두고 그쪽을 편성한다. 유튜브 소스는 아카이브 탐색·프리뷰·비중요 편성용으로 쓴다. — **Cloudflare/Bunny를 백본으로, 유튜브를 보조로 두는 것이 이 제품의 기본 권장 구성이다.**

### 3.3 채널 (P0)

**채널은 "독립된 하나의 송출 라인"입니다.** 라이브러리는 전 채널이 공유하고, 그 외 모든 것은 채널마다 독립입니다.

```
Channel {
  id, name
  masterResolution  편성·렌더 기준 해상도
                    3840x2160 | 1920x1080 | 1080x1920 | 2160x3840 | custom
  outputs           Output[]   ← 1개 이상. 스위처/모니터/NDI 혼합 가능 (§3.7)
  rundownId         현재 편성
  fillerPolicy      필러 자동 선정 규칙 (§3.6)
  standbyScreen     대기 화면 (로고) 설정 (§3.9)
  switcher          { type: obs|vmix, host, port, auth, sceneMap }
  state             stopped | running | recovering
}
```

원칙
- **격리**: 한 채널의 장애·재기동이 다른 채널에 영향을 주지 않는다. **출력마다** 독립된 출력창 프로세스와 워치독을 가지므로, 격리는 채널 안에서 출력 단위로 한 번 더 이뤄진다.
- **공유**: 라이브러리·소스 자격증명·메타데이터 캐시는 전 채널이 공유한다. 같은 영상을 두 채널이 동시에 편성해도 문제없다.
- **독립 편성**: 채널마다 다른 런다운. 같은 런다운을 여러 채널에 복사할 수는 있다.
- **출력 다중화**: 한 채널이 여러 출력을 가진다. 모든 출력은 **같은 편성·같은 시점**을 재생하며, 해상도·스케일·오디오만 출력마다 다르다. 화면마다 *다른 편성*이 필요하면 그건 채널을 나누는 것이다.

**채널 수 상한은 하드웨어가 결정합니다.** 앱은 상한을 강제하지 않되, **채널 추가 시 예상 디코더 부하와 현재 여유를 표시하고 경고**합니다. 실제 한계치는 2단계에서 실측해 권장 구성표로 문서화합니다 (§6.2).

### 3.4 오디오 라우팅 (P0)

**두 방식을 모두 지원하되, 다채널에서는 사실상 하나만 유효합니다.**

| 모드 | 동작 | 적합한 경우 | 한계 |
|------|------|-------------|------|
| **시스템 기본** | OS 기본 출력으로 재생 → OBS "데스크톱 오디오"로 캡처 | **단일 채널**. 설정 없이 바로 동작 | 여러 채널이 한 버스에 섞인다. 채널 분리 불가 |
| **전용 장치** | 채널마다 다른 출력 장치로 라우팅 → OBS가 장치별로 개별 캡처 | **다채널**. 채널별 볼륨·믹싱 독립 | 가상 오디오 장치 설치 필요 |

구현: Electron(Chromium)의 `setSinkId`로 **출력별** 오디오 장치를 지정합니다. A/B 두 레이어 모두 같은 sink로 설정해야 전환 시 소리가 끊기지 않습니다.

**미러 출력의 오디오 — 반드시 하나만 활성**

한 채널을 여러 모니터에 띄우면 각 출력창이 같은 콘텐츠를 재생하므로, 그대로 두면 **소리가 겹쳐 에코가 발생**합니다. 따라서 출력마다 `audioEnabled` 플래그를 두고 **채널당 정확히 하나의 출력만 오디오를 낼 수 있게** 강제합니다. 나머지는 자동 음소거됩니다.

- 새 출력을 추가하면 기본값은 음소거. 첫 번째 출력만 오디오 활성.
- 오디오 담당 출력을 바꾸면 이전 것은 즉시 음소거된다.
- 오디오 담당 출력이 장애로 내려가면 다음 출력이 자동으로 승계한다.

전용 장치 모드에 필요한 가상 오디오 드라이버
- **macOS**: BlackHole (다중 채널이면 인스턴스 여러 개, 또는 16ch 버전을 채널별 페어로 분배)
- **Windows**: VB-Cable (다중 인스턴스) 또는 VoiceMeeter

앱은 드라이버를 설치하지 않습니다. 대신 **설정 화면에서 사용 가능한 출력 장치를 나열하고, 채널 수보다 장치가 부족하면 경고와 함께 설치 안내를 표시**합니다.

> **정책**: 2채널 이상을 만들면 앱이 전용 장치 모드를 권장하고, 시스템 기본 모드를 유지할 경우 "채널 오디오가 섞입니다"라고 명시적으로 경고한다.

### 3.5 편성 파이프라인 (P0 / P1)

**편성은 세 단계를 거칩니다.** 운영자가 손으로 하는 것은 1단계뿐이고, 2·3단계는 버튼 하나로 끝납니다.

```
1. 편성 블록      어느 소스 그룹을 → 기간 × 요일(복수) × 시간대(복수)에 배치
        ↓          ← 운영자가 직접 하는 유일한 작업
2. 자동 채움      블록이 없는 나머지 모든 시간을 지정 소스로 채움
        ↓          ← 버튼 하나
3. 런다운 생성    날짜별 실제 재생 목록. 시작 시각이 초 단위로 확정됨
        ↓
4. 미세 조정      드래그·마커로 손보기 (§4.3.4)
        ↓
   확정 · 송출
```

이 구조의 핵심은 **1단계가 "규칙"이고 3단계가 "산출물"**이라는 점입니다. 블록을 고치면 런다운은 다시 생성됩니다.

#### 3.5.1 편성 블록 (Block)

운영자가 다루는 편성의 최소 단위입니다. **개별 영상이 아니라 "어느 그룹을 언제"**를 지정합니다.

```
Block {
  id, name
  poolId          소스 그룹 (폴더 / 유튜브 재생목록 / CF·Bunny 라이브러리)
  dateFrom, dateTo  기간
  days            요일 [0..6]  ← 복수 선택
  slots           [[시작, 종료], ...]  ← 복수 시간대
  order           seq | random | unaired    재생 순서
  fit             loop | filler | trim      시간이 남거나 모자랄 때
}
```

| 항목 | 설명 |
|------|------|
| **소스 그룹** | 개별 영상이 아니라 폴더·재생목록·라이브러리 단위. 파일이 추가되면 다음 생성 때 자동 반영 |
| **기간** | 시작일~종료일. 기간이 끝나면 그 시간대는 자동 채움으로 넘어간다 |
| **요일 · 복수** | 예) 월·수·금 — 한 블록이 여러 요일에 동시에 적용된다 |
| **시간대 · 복수** | 예) 09:00–12:00 그리고 19:00–21:00 — 하루에 여러 구간 |
| **재생 순서** | 순차 / 랜덤 / **미방영 우선**(오래 안 나간 것부터) |
| **시간 맞춤** | **반복**(그룹을 다시 처음부터) / **필러**(한 바퀴 뒤 남는 시간은 브리지·스팟) / **잘라내기**(끝에 걸치는 영상을 잘라 정확히 맞춤) |

- **블록 시작 시각에는 Hard 마커가 자동으로 붙습니다** (§3.5.4). "10시 특강"이 10:00:00에 시작하지 않으면 블록의 의미가 없기 때문입니다.
- 블록끼리 시간대가 겹치면 편집 중에 즉시 경고합니다. 겹침은 허용하지 않습니다.

#### 3.5.2 자동 채움

**블록이 없는 모든 시간을 한 번에 채워 24시간 편성을 완성하는 단계입니다.**

```
AutoFill {
  enabled      켜기/끄기
  poolIds      채움 소스 그룹 (복수)
  order        seq | random | unaired
}
```

- 켜면 주간 그리드의 빈 구간이 전부 채워지고, 커버리지가 100%가 된다.
- 끄면 그 시간은 편성 공백이 되고, 런다운에 경고가 뜬다(대기 화면 = 로고, §3.9).
- 채움 소스는 블록과 별개로 지정한다. 통상 브리지·스팟·재방송 아카이브를 섞는다.

> **이것이 "수동 편성인데 일부는 자동"의 실체입니다.** 운영자는 중요한 시간대만 블록으로 직접 잡고, 나머지 빈 시간은 신경 쓰지 않습니다.

#### 3.5.3 런다운 (생성 결과)

블록과 자동 채움을 특정 날짜에 적용해 만들어지는 **실행 가능한 재생 목록**입니다.

```
Rundown {
  id, channelId, date
  generatedFrom   { blockIds, autoFillHash }   재생성 추적용
  edited          손으로 수정했는지 여부
  items: [
    { itemId, order, blockName,
      startAtEstimated,   누적 계산된 시작 시각
      startAtFixed,       고정 시각
      timingMode,         none | hard | soft | notBefore
      trimIn, trimOut,
      pinned,             재생성해도 보존
      onAirRules }
  ]
}
```

- **생성 시점**: 매일 D-1에 자동 생성 + 언제든 수동 재생성.
- **재생성과 수동 편집의 충돌**: 손으로 고친 런다운을 다시 생성하면 수정분이 사라집니다. 이때는 반드시 확인을 받고, **`pinned` 표시된 항목은 재생성해도 보존**합니다.
- 런다운에는 항목이 어느 블록에서 왔는지 표시됩니다(`blockName`). 문제가 생겼을 때 블록으로 거슬러 올라갈 수 있어야 하기 때문입니다.

#### 3.5.4 고정 시각 마커 3종

방송 자동화 도구들이 공통으로 쓰는 세 가지 모델을 그대로 채택합니다 (PlayIt Live 등, 부록 B). "정시에 시작"이라는 요구는 실제로 세 가지 다른 의미이며, 하나로 뭉뚱그리면 반드시 운영 중에 문제가 됩니다.

| 마커 | 기호 | 동작 | 쓰는 상황 |
|------|------|------|-----------|
| **Hard** | 🔴 | 그 시각이 되면 **재생 중인 항목을 끊고** 시작 | **블록 시작 시각에 자동 부여.** 정시 뉴스, 계약된 광고 |
| **Soft** | 🟡 | 앞 항목이 **끝나기를 기다렸다가** 시작 (밀림 허용) | 화면이 잘리는 것이 더 나쁜 경우 |
| **Not Before** | 🔵 | 그 시각 **전에는 시작하지 않음.** 일찍 끝나면 필러 | 특정 시각 이후에만 나가야 하는 콘텐츠 |
| (없음) | — | 앞 항목에 이어서 자연스럽게 | 블록 안의 나머지 항목 |

- **Hard**는 앞 항목을 자르므로 편집 화면에서 "N초 잘림"을 미리 경고한다.
- **Not Before**는 공백을 만들 수 있으므로 자동으로 필러 후보를 제안한다.
- 마커 간 충돌은 저장 시점이 아니라 **편집 중에 즉시** 경고한다.

### 3.6 필러 자동 선정 (P1)

**필러는 편성 공백과 장애 상황에서 대신 나가는 예비 콘텐츠**이며, 운영자가 매번 지정하지 않고 자동 선택합니다.

선정 규칙 (우선순위 순)

1. **로컬 재생 가능한 항목만** (`isLocal = true`) — 필러가 필요한 상황은 대개 네트워크 장애다. 클라우드 필러는 정작 필요할 때 못 쓴다.
2. **길이 적합성** — 메워야 할 공백에 가장 잘 맞는 길이. 넘치면 트림 가능한 항목 우선.
3. **최근 재생 회피** — 최근 N시간 내 나간 항목은 후보에서 제외 (같은 필러 반복 방지).
4. **필러 풀 제한** — 운영자가 태그나 폴더로 "필러 후보 풀"을 지정했으면 그 안에서만 고른다. 미지정 시 라이브러리 전체의 로컬 항목.

```
FillerPolicy {
  poolTag         후보 풀 (미지정 시 로컬 전체)
  avoidRecentHours 기본 6시간
  allowTrim       공백에 맞춰 잘라 쓸지 여부
  lastResort      모든 조건 실패 시 쓸 고정 루프 클립 (선택)
}
```

**사전 캐시**: 앱은 필러 후보 중 상위 몇 개를 항상 프리로드 가능 상태로 유지해, 장애 발생 시 대기 없이 즉시 전환합니다.

**최후 수단 체인**: 필러 후보 없음 → `lastResort` 클립 → **로고 대기 화면** (§3.9). 어느 단계로 내려가든 이력에 기록하고 경고합니다. **완전한 검은 화면은 어떤 경우에도 나가지 않습니다** — 최악의 경우에도 로고가 표시됩니다.

### 3.7 출력 대상 (P0)

**하나의 채널은 여러 출력을 가질 수 있고, 출력마다 목적지가 다릅니다.** 이것이 v1.2에서 가장 크게 바뀐 부분입니다.

```
Output {
  id, channelId
  type            monitor | capture_window | ndi
  displayId       monitor / capture_window 에서 사용할 모니터
  resolution      이 출력의 픽셀 해상도 (미지정 시 모니터 해상도 자동 감지)
  scaleMode       none(1:1) | fit(여백맞춤) | fill(꽉채움) | stretch(늘림)
  audioEnabled    이 출력에서 소리를 낼지 (채널당 1개만 true)
  audioDeviceId   audioEnabled일 때 사용할 출력 장치
  state           stopped | running | recovering
}
```

#### 세 가지 출력 유형

| 유형 | 최종 목적지 | 창의 성격 | 제약 |
|------|-------------|-----------|------|
| **모니터 직출력** (`monitor`) | 연결된 모니터 = **최종 화면** | 지정 모니터에 전체화면. 커서·메뉴바까지 덮음 | 물리 모니터가 실제로 연결돼 있어야 함 |
| **스위처 공급 — 창 캡처** (`capture_window`) | OBS·vMix가 캡처 → 인코딩 | 프레임리스 창. UI 없음 | **창 픽셀 수만큼의 실제 디스플레이 표면 필요.** 1080p 창은 고해상도 모니터 한 대에 여러 개 배치할 수 있어 현실적 부담이 작다 |
| **스위처 공급 — NDI** (`ndi`, 조건부 P2) | OBS·vMix가 NDI 수신 | 화면 없이 스트림만 | NDI 런타임 필요, LAN 대역폭 |

**조합이 가능합니다.** 채널 1이 `capture_window`(OBS용) + `monitor`(대기실 화면) + `monitor`(로비 화면)를 동시에 가질 수 있습니다.

#### 출력 개수 상한

**모니터 직출력은 한 PC에 최대 4대로 한정합니다.** 물리 모니터 1대가 출력 1개를 담당하므로, 전 채널을 통틀어 `monitor` 유형 출력은 4개를 넘지 않습니다.

- 앱은 감지된 모니터가 4대를 넘어도 **선택 가능한 대상은 4개까지**로 제한한다.
- 스위처 공급 출력(`capture_window` / `ndi`)은 이 상한과 별개로 계산한다.
- 4대는 **설계 상한이자 성능 검증 기준**이다 (§6.2). 그 이상은 지원 범위 밖이며, OS 미러링이나 NDI 분배로 처리한다.

#### 출력창 공통 요건

- 프레임리스, 지정 해상도로 픽셀 고정. 창 크기 변경 불가.
- UI 크롬·커서·툴팁·알림 없음. 배경은 순수 검정.
- 편성이 없거나 복구 중이면 **로고 대기 화면** (§3.9).
- 크래시 시 **해당 출력만** 자동 재기동 + 런다운 현재 지점 복귀. 같은 채널의 다른 출력은 계속 재생.

지원 해상도: **1920×1080 (기본)**, 1080×1920(세로), 사용자 지정.

#### 4K 보류 (2026-08-27 결정)

**4K는 전면 보류합니다.** 지원 해상도 목록에서 제외하며, 개발·검증·권장 구성 산정을 전부 1080p 기준으로 진행합니다.

데이터 모델(`Output.resolution`)은 임의 해상도를 받도록 두되, **4K는 지원·검증 대상이 아닙니다.** 라이브러리의 `maxResolution`(§3.1)은 계속 수집합니다 — 나중에 판단할 때 필요한 정보이고 수집 비용이 없기 때문입니다.

**재개할 때 먼저 확인할 것** (지금 조사하지 않되, 다시 발견하지 않도록 남깁니다)

1. **창 캡처의 디스플레이 표면 제약** — 4K 창을 캡처하려면 실제 4K 픽셀의 표면(4K 모니터 / 더미 HDMI·EDID 에뮬레이터 / macOS 가상 디스플레이)이 필요하다. 여기가 막히면 NDI를 선행해야 하므로 일정이 바뀐다
2. **하드웨어 한계** — 4K는 출력 1개당 디코더 부담이 크다. 다채널·미러와 겹치면 급격히 불가능해진다
3. **소스 쪽 통제 문제** — 4K 원본은 주로 본인 유튜브 채널에 있는데, 유튜브 IFrame 임베드는 **재생 품질을 앱이 지정할 수 없다**(대역폭·뷰포트에 따라 자동 조정). 4K를 안정적으로 내보내려면 본인 4K 마스터를 Cloudflare Stream 또는 Bunny Stream에 올려 그쪽을 편성해야 한다 — §3.2가 무결절 때문에 권고한 것과 같은 구성이다

#### 스케일 모드 — 모니터마다 다른 해상도 대응

채널의 `masterResolution`과 출력 모니터의 실제 해상도가 다를 때 처리 방식입니다. CMS에서 검증된 네 가지를 그대로 가져옵니다.

| 모드 | 동작 | 쓰임 |
|------|------|------|
| `none` (1:1) | 스케일 없이 원본 픽셀 그대로 | 해상도가 정확히 일치할 때. **무왜곡** |
| `fit` (여백맞춤) | 비율 유지, 남는 곳은 검은 여백 | 기본값. **왜곡 없음** |
| `fill` (꽉채움) | 비율 유지, 넘치는 부분은 잘림 | 화면을 꽉 채워야 할 때 |
| `stretch` (늘림) | 비율 무시하고 늘림 | 특수 비율 화면. 왜곡 발생 |

출력을 추가하면 **해당 모니터의 해상도를 자동 감지**해 채우고, 채널 기준 해상도와 다르면 `fit`을 기본 제안합니다.

#### 미러 출력의 동기화 (P1)

같은 채널의 여러 출력은 각자 독립된 `<video>`로 재생하므로 **완전한 프레임 동기는 보장되지 않습니다.** 실용적으로 다음과 같이 다룹니다.

1. 모든 출력이 서버의 같은 지시(directive)를 받아 같은 항목을 같은 시점에 시작한다.
2. 채널의 첫 번째 출력을 **기준(primary)**으로 삼아 재생 위치를 주기적으로 브로드캐스트한다.
3. 다른 출력이 기준과 **±100ms를 넘게 벌어지면 자동 seek 보정**한다.
4. 항목 전환 시점은 서버 지시로 맞추므로 전환이 어긋나 보이지는 않는다.

> **주의**: 모니터 두 대를 **나란히 붙여** 같은 영상을 띄우는 배치에서는 100ms 편차도 눈에 띌 수 있습니다. 그런 경우는 앱 미러가 아니라 **OS 디스플레이 미러링**(macOS 디스플레이 복제 / Windows 복제)을 쓰는 것을 권장합니다. 이때 Live Player는 출력 1개만 만들고 OS가 복제를 담당합니다.

#### 자원 부하

**미러 출력 N개는 디코딩 부하도 N배입니다.** 각 출력창이 독립적으로 디코딩하기 때문입니다. 채널 수와 마찬가지로, 출력 추가 시 예상 부하와 현재 여유를 표시하고 경고합니다 (§6.2).

상한인 **모니터 4대를 모두 쓰는 구성은 부하가 만만치 않습니다.**

| 구성 | 앱 미러 (출력 4개) | OS 디스플레이 미러링 (출력 1개) |
|---|---|---|
| 1080p60 × 4대 | 디코딩 4개 — **상급 하드웨어 필요** | 디코딩 1개 — 대부분 가능 |
| 1080p30 × 4대 | 디코딩 4개 — 중급에서 가능 | 디코딩 1개 — 대부분 가능 |

> **4대에 같은 화면을 띄우는 것이 목적이라면 OS 디스플레이 미러링을 쓰십시오.** 앱 미러가 필요한 경우는 모니터마다 해상도·비율이 달라 스케일 모드를 따로 줘야 할 때뿐입니다. 앱은 출력 3개 이상을 추가할 때 이 안내를 표시합니다.

부하를 줄이는 선택지
- 같은 화면을 여러 모니터에 → **OS 디스플레이 미러링** 사용 (디코딩 1회)
- 채널 하나를 여러 곳에 → **NDI 1개 출력** 후 vMix/OBS에서 분배

**OBS 브라우저 소스는 1차 지원 대상에서 제외합니다** — 내장 CEF의 유튜브 임베드·DRM 처리 문제 때문입니다.

### 3.8 장애 복구 (P1)

무인 24시간 운영이 목표이므로 실패를 전제로 설계합니다. **복구는 채널 단위, 그 안에서 다시 출력 단위로 격리됩니다.**

| 상황 | 대응 |
|------|------|
| 다음 항목 프리로드 실패 | 즉시 그 다음 항목으로 스킵, 실패 기록 |
| CDN 응답 없음 (CF 또는 Bunny) | `mirrorOf`로 묶인 반대편 소스로 자동 전환 |
| 스킵할 항목도 없음 | **자동 선정된 필러** 재생 (§3.6) |
| 필러도 없음 | `lastResort` 클립 → **로고 대기 화면** (§3.9). 검은 화면은 나가지 않음 |
| 네트워크 끊김 | 로컬 캐시 항목으로 자동 전환 |
| 출력창 응답 없음 | 워치독이 감지 → **그 출력만** 재기동 → 런다운 현재 지점 복귀. 같은 채널의 다른 출력은 계속 재생 |
| 오디오 담당 출력이 내려감 | 같은 채널의 다음 출력이 오디오를 자동 승계 |
| 모니터 연결 해제 | 해당 출력을 `stopped`로 전환하고 경고. 재연결 시 자동 복귀. 다른 출력·채널은 무영향 |
| 미러 출력 간 재생 위치 어긋남 | 기준 출력 대비 ±100ms 초과 시 자동 seek 보정 (§3.7) |
| 서버 프로세스 종료 | 자동 재시작 후 running 상태였던 채널·출력 전부 복구 |
| 디코더 자원 부족 | 우선순위 낮은 채널의 프리로드를 지연시켜 피크 회피, 경고 표시 |

### 3.9 대기 화면 (P0)

**편성이 비어 있는 시간과 모든 복구 수단이 소진된 상황에 표시되는 화면입니다. 로고를 띄웁니다.**

검은 화면을 기본값으로 두지 않는 이유는 두 가지입니다. 모니터 직출력에서는 검은 화면이 "장비 고장"으로 오인되고, 스위처 공급에서는 OBS 쪽에서 신호 유실과 구분되지 않습니다. **로고는 "정상 동작 중이며 지금은 편성이 없다"는 신호**입니다.

```
StandbyScreen {
  logoPath          로고 이미지 (PNG 권장, 투명 배경)
  backgroundColor   배경색 (기본 #000000)
  logoScale         화면 대비 로고 폭 비율 (기본 20%)
  logoPosition      center | 9분할 위치 지정
  fadeMs            영상 ↔ 대기 화면 전환 페이드 (기본 500ms)
}
```

- 채널마다 설정하며, 앱 전역 기본값을 상속받는다.
- 로고 미등록 시 앱 기본 로고를 표시한다. **어떤 경우에도 순수 검은 화면으로 두지 않는다.**
- 전환은 페이드로 처리해 컷 전환의 깜박임을 피한다.
- 대기 화면 진입·이탈은 **모두 재생 이력에 기록**한다. 계획된 공백인지 장애로 인한 것인지 구분해 남긴다.

| 진입 사유 | 이력 기록 | 경고 |
|---|---|---|
| 편성 공백 (런다운에 항목 없음) | `standby_scheduled` | 없음 |
| 필러·최후수단 모두 소진 | `standby_failure` | **경고 발생** |
| 출력 복구 중 | `standby_recovering` | 경고 발생 |

### 4.3 편성 화면 설계 (핵심 화면)

**편성 화면이 이 제품에서 사람이 가장 오래 머무는 곳입니다.** 동종 제품 조사(부록 B) 결과와 §3.5 파이프라인을 반영해 아래에 정의합니다.

#### 4.3.1 두 개의 뷰

파이프라인의 1·2단계와 3·4단계는 다루는 대상이 다르므로 화면을 나눕니다. 같은 자리에서 탭으로 전환합니다.

| 뷰 | 다루는 것 | 단위 |
|----|-----------|------|
| **주간 편성** | 편성 블록 배치 + 자동 채움 | 요일 × 시간대 (규칙) |
| **런다운** | 생성된 하루치 재생 목록 | 항목 (실행) |

> **주간 편성에서 규칙을 놓고, 런다운에서 결과를 확인한다.** 두 화면을 오가는 것이 기본 작업 흐름입니다.

#### 4.3.2 핵심 판단 — 각 뷰의 형식은 다르다

- **주간 편성은 그리드가 맞습니다.** 반복되는 주간 규칙을 다루므로 요일 × 시간 격자가 가장 직관적입니다. CMS의 편성표와 형식이 같습니다.
- **런다운은 리스트가 맞습니다.** 하루 150~300개 항목을 시간 축에 배치하면 짧은 클립이 몇 픽셀이 되고 드래그가 불가능해집니다. 조사한 프로 도구들이 예외 없이 리스트를 주 편집 화면으로 쓰는 이유입니다.

> 앞선 버전에서 "그리드를 쓰지 않는다"고 적었으나, 이는 **런다운에 한정된 판단**으로 정정합니다. 규칙 배치에는 그리드가, 실행 목록에는 리스트가 맞습니다.

#### 4.3.5 공백·초과는 인라인으로

별도 "검증" 버튼을 만들지 않습니다. 문제가 있으면 **그 자리에 액션이 달린 경고 행**이 나타납니다.

```
⚠ ─── 3분 12초 공백 ───   [필러 채우기]  [앞 항목 늘리기]
🔴 ─ 앞 항목 05:45 잘림 ─  [Soft로 변경]  [앞 항목 자르기]
⚠ ─ 06:00~09:00 편성 없음 ─ [자동 채움 켜기]
```

문제를 찾는 것과 고치는 것이 같은 자리에서 끝나야 합니다. 마지막 항목처럼 **주간 편성으로 되돌아가야 하는 문제도 런다운에서 바로 해결**할 수 있어야 합니다.

#### 4.3.6 드래그 편의 기능

- **라이브러리 → 런다운**: 삽입 위치에 파란 선 + **예상 시작 시각 툴팁**
- **OS 파일 탐색기 → 런다운**: 파인더·탐색기에서 직접 끌어다 놓기 (Electron이므로 가능)
- `Alt` + 드래그 = 복제
- 주간 편성에서는 **소스 그룹을 블록에 끌어다 놓아** 그룹을 교체

#### 4.3.7 온에어 중 편집과 보호

온에어 중 편집은 조사한 모든 프로 도구의 핵심 기능이며, 우리도 지원합니다. 다만 사고 방지 장치를 둡니다.

- **현재 재생 항목과 다음 1개는 드래그 잠금.** 자물쇠를 명시적으로 풀어야만 건드릴 수 있다
- 그 외 편집은 **즉시 반영 + `Cmd+Z` 되돌리기**. "적용" 커밋 단계는 두지 않는다
- **블록을 고쳐도 오늘 방송 중인 런다운은 자동으로 바뀌지 않는다.** 재생성은 명시적 행동이어야 한다

### 4.4 출력 관리 화면 설계

편성 다음으로 중요한 화면입니다. **모니터·창 캡처·NDI를 채널에 배정하고, 해상도·스케일·오디오를 출력마다 맞추는 곳**입니다(§3.7).

#### 4.4.1 핵심 판단 — 모니터는 공간이므로 지도로 보여준다

출력 목록을 표로만 보여주면 "모니터 2번"이 물리적으로 어디 있는 화면인지 알 수 없습니다. 운영자는 책상 위 배치로 기억하지 번호로 기억하지 않습니다.

> **OS의 디스플레이 설정과 같은 배치도를 그대로 씁니다.** 감지된 모니터를 실제 상대 위치·비율로 그리고, 그 위에 배정 상태를 표시합니다. 새로 배우지 않아도 됩니다.

#### 4.4.2 모니터는 전역 자원, 출력은 채널 소유

이 화면의 가장 중요한 규칙입니다.

- **모니터 1대는 출력 1개만 담을 수 있습니다.** 채널 2개가 같은 모니터를 쓸 수 없습니다.
- 따라서 배치도는 **전 채널 기준으로 그리고**, 각 모니터에 누가 쓰는지 표시합니다 — `이 채널` / `채널 2` / `비어 있음` / `연결 끊김`.
- 다른 채널이 쓰는 모니터를 클릭하면 **"채널 2에서 가져올까요?"**를 묻습니다. 조용히 뺏지 않습니다.
- **모니터 출력은 전 채널 통틀어 최대 4개**입니다(§3.7). 상한에 닿으면 추가 버튼이 비활성화되고 이유를 표시합니다.

#### 4.4.4 모니터 배치도

| 요소 | 동작 |
|------|------|
| **상대 위치·비율** | OS가 보고하는 배치 그대로. 세로 모니터는 세로로 그린다 |
| **표시 정보** | 번호 · 해상도 · 배정된 채널 · 주 모니터 표시 |
| **빈 모니터 클릭** | 현재 채널에 모니터 출력을 추가한다. 해상도는 자동 감지 |
| **이 채널 모니터 클릭** | 그 출력을 선택해 인스펙터를 연다 |
| **다른 채널 모니터 클릭** | "채널 N에서 가져올까요?" 확인 후 이동 |
| **연결 끊김** | 회색 + 경고 아이콘. 해당 출력은 `stopped`이며 재연결 시 자동 복귀(§3.8) |
| **식별** | `모니터 번호 표시` 버튼 — 각 화면에 큰 숫자를 띄워 실물과 대조 (OS 기능과 동일) |

#### 4.4.5 출력 목록

행마다 유형 아이콘 · 이름 · 해상도 · 스케일 모드 · **오디오 표시** · 상태 배지.

**오디오는 라디오 버튼처럼 동작합니다.** 채널당 정확히 하나만 소리를 낼 수 있으므로(§3.4), 한 출력의 🔊를 켜면 나머지는 자동으로 음소거됩니다. 체크박스로 만들면 두 개를 켤 수 있다고 오해하게 됩니다.

`+ 출력 추가`는 세 가지를 제시합니다 — **모니터 직출력** / **창 캡처(OBS·vMix용)** / **NDI**. NDI는 조건부 기능이므로 미구현 단계에서는 비활성 + 사유 표시.

#### 4.4.6 출력 상세 (인스펙터)

| 항목 | 내용 |
|------|------|
| **유형** | 생성 후 변경 불가. 바꾸려면 삭제하고 다시 만든다 |
| **대상 모니터** | `monitor` 유형만. 배치도와 연동해 선택 |
| **해상도** | 모니터 해상도를 자동 감지해 채움. 사용자 지정 가능 |
| **스케일 모드** | 1:1 / 여백맞춤 / 꽉채움 / 늘림 — **각 모드를 도형 미리보기로 보여준다** |
| **오디오** | 이 출력에서 소리를 낼지 + 출력 장치 선택. 켜면 다른 출력은 자동 음소거 |
| **상태** | `running` / `stopped` / `recovering` + 마지막 오류 |

**스케일 모드는 말로 설명하면 안 됩니다.** "여백맞춤"과 "꽉채움"의 차이는 도형 두 개면 즉시 이해되지만 문장으로는 매번 헷갈립니다. 소스 사각형과 출력 사각형을 겹쳐 그린 작은 미리보기를 모드마다 붙입니다.

#### 4.4.7 부하 미터와 안내

출력 수가 곧 디코더 부담입니다(§3.7). 화면 하단에 항상 표시합니다.

- `디코더 2 / 권장 4` 형태. 권장치는 2단계에서 실측한 하드웨어 등급표(§6.2) 기준
- 초과하면 경고로 바뀌고, 추가는 막지 않되 이유를 설명한다
- **출력을 3개 이상 추가하려 하면 OS 디스플레이 미러링 안내를 표시한다**(§3.7). 같은 화면을 여러 모니터에 띄우는 것이 목적이라면 앱 미러보다 OS 미러링이 낫다
- 모니터 출력이 4개에 닿으면 추가 버튼 비활성화 + `모니터 출력은 최대 4개입니다`

#### 4.4.8 미리보기

각 출력의 현재 화면을 작은 썸네일로 보여줍니다. **"내가 배정한 모니터에 정말 그 화면이 나가고 있나"를 자리에서 확인할 수 있어야** 합니다 — 특히 모니터가 다른 방에 있을 때.

### 4.5 UI 원칙

| 원칙 | 내용 |
|------|------|
| **다크 테마 기본** | 방송 현장·행사장은 어둡다. 밝은 화면은 모니터 확인을 방해한다 |
| **명령 팔레트** | `Cmd+K`로 전 기능 접근. 팔레트가 있으면 메뉴바를 거의 없앨 수 있다 |
| **키보드 우선** | `↑↓` 이동 · `Space` 미리보기 · `Delete` 삭제 · `Cmd+D` 복제 · `F` 필러 삽입 · `Cmd+Z` 되돌리기 |
| **즉시 반영 + 되돌리기** | 저장 버튼·확인 대화상자를 최소화한다. 실수는 되돌리기로 해결 |
| **인라인 해결** | 경고는 문제가 있는 자리에, 고치는 버튼과 함께 |
| **한 화면에서 끝내기** | 편성 작업은 화면 전환 없이 완료된다 |

#### 만들지 않을 것 (안티패턴)

조사한 프로 도구들의 공통된 함정입니다. 전부 "단순·심플·현대적"의 반대편입니다.

- **다중 창 도킹 레이아웃** — 자유도가 높아 보이지만 매번 창을 정리해야 한다
- **컬럼 20개짜리 그리드** — 방송국 트래픽 시스템의 유산. 우리 사용자에게 불필요
- **규칙 빌더 / 조건식 편집기** — 배워야 하는 순간 진입 장벽이 된다. 편성 블록(§3.5.1)은 규칙이지만 **조건식이 아니라 그리드 위의 위치**로 표현되므로 여기 해당하지 않는다. 블록 설정은 "무엇을·언제" 여섯 항목이 전부여야 한다
- **별도 컴파일·검증 단계** — 편집과 검증이 분리되면 사용자가 검증을 건너뛴다
- **모달 대화상자 연쇄** — 인스펙터 패널로 대체

## 5. 기술 구성

### 5.1 플랫폼

**Electron 데스크톱 앱 (macOS · Windows)**

웹앱이 아니라 데스크톱 앱이어야 하는 이유:
- 출력창의 크기·위치·크롬을 픽셀 단위로 통제해야 캡처가 안정적이다
- 채널·출력별 오디오 장치 라우팅이 필요하다
- **모니터를 감지해 지정 화면에 완전 전체화면으로 띄우는 것**은 웹으로 불가능하다
- 로컬 폴더 접근·감시가 필요하다
- 멀티모니터 지정 출력이 필요하다
- 24시간 무인 운영을 위한 워치독·자동 재기동이 필요하다
- NDI 출력에는 네이티브 바인딩이 필요하다

### 5.2 기술 스택

| 영역 | 선택 | 근거 |
|------|------|------|
| 셸 | Electron | CMS에서 검증된 배포·서명·업데이트 파이프라인 재사용 |
| 서버 | Node.js + Express | 단일 프로세스, 로컬 미디어 Range 스트리밍 |

| 영속성 | JSON 파일 스토어 | 라이브러리·채널·런다운 규모에 충분. DB 도입은 과함 |
| 편성 리스트 DnD | SortableJS | 프레임워크 독립. 무거운 트리를 들이지 않음 (§5.5) |
| 타임라인 리본 | Canvas 2D (자체 구현) | 항목 수와 무관한 렌더 비용. 라이브러리 불필요 |

│  │   ├ 채널 매니저          ← 채널 생명주기·자원 예산       │

**서버가 진실의 원천**입니다. 매초 각 채널의 현재 시각을 기준으로 "이 채널이 지금 무엇을 재생해야 하는가"를 계산해 해당 출력창과 콘솔에 브로드캐스트합니다. 출력창은 판단하지 않고 지시받은 것을 재생합니다 — CMS에서 검증된 구조를 채널 수만큼 복제한 형태입니다.

**채널 매니저**는 채널 생명주기(생성·시작·정지·재기동)를 관리하고, 디코더·대역폭 예산을 추적해 프리로드 타이밍을 채널 간에 분산시킵니다.

**출력 매니저**는 v1.2에서 새로 들어간 계층입니다. 연결된 모니터를 감지·추적하고(연결 해제·해상도 변경 대응), 출력창의 생성·배치·전체화면을 담당하며, 같은 채널에 속한 출력들의 재생 위치 드리프트를 보정합니다. 오디오 담당 출력이 채널당 하나만 유지되도록 강제하는 것도 이 계층입니다.

> 채널 수를 N, 채널당 출력 수를 M이라 하면 **출력창은 총 ΣM개**이며, 디코딩 부하도 여기에 비례합니다.

### 5.4 편성 화면의 성능 판단

**가상 스크롤을 도입하지 않습니다.**

일반적으로 리스트 항목이 500개를 넘으면 가상 스크롤을 고려하지만, 드래그앤드롭과 가상화를 함께 쓰면 스크롤 끊김과 transform 충돌이 잘 알려진 문제입니다 (dnd-kit 이슈 다수, 부록 B).

우리는 그 상황을 피할 수 있습니다.

| 조건 | 값 |
|------|-----|
| 편성 단위 | **하루** (24시간) |
| 평균 항목 길이 | 5~10분 가정 |
| 하루 항목 수 | **약 150~300개** |
| 판단 | 순수 DOM으로 충분. 가상화 불필요 |

- **리스트**: DOM + SortableJS — 300개 규모에서 문제없음
- **리본**: canvas 1개 — 항목 수와 무관
- 여러 날을 한 화면에 펼치지 않는다. 날짜 전환으로 처리한다.

> 항목이 예상보다 많아지는 경우(짧은 클립 위주 편성)에 대비해, 2단계에서 **1,000개 항목으로 드래그 반응성을 실측**합니다. 기준 미달 시에만 가상화를 검토합니다.

## 6. 제약 조건

### 6.1 콘텐츠 정책 — 본인 소유 콘텐츠 한정

**Live Player는 운영자 본인이 소유·관리하는 채널·계정의 콘텐츠만 등록 대상으로 합니다.**

- 유튜브 소스는 **OAuth로 인증한 본인 채널의 영상·재생목록만** 등록 가능하도록 구현한다. 임의의 유튜브 URL 붙여넣기는 허용하지 않는다.
- Cloudflare Stream·Bunny Stream은 운영자 본인 계정의 라이브러리만 연결한다.
- 로컬 파일·폴더는 운영자 책임 영역이다.

이 제약은 저작권과 각 서비스 이용약관 준수를 위한 것이며, **기능 편의를 이유로 완화하지 않습니다.**

### 6.2 성능 · 자원

- **전환 품질**: 항목 전환 시 검은 프레임 0 (유튜브 소스 제외 — best-effort).
- **정시성**: 고정 시각 항목의 시작 오차 ±1초 이내. 채널 수와 무관.
- **연속 운영**: 72시간 무중단 재생 시 메모리 누수로 인한 성능 저하 없을 것.
- **모니터 직출력 상한**: **한 PC에 최대 4대.** 설계 상한이자 성능 검증 기준 (§3.7).
- **채널 수 · 스위처 출력 수**: 앱은 상한을 강제하지 않는다. 대신 채널·출력 추가 시 예상 부하를 표시하고, **2단계에서 실측한 권장 구성표**를 제공한다.
- **미러 출력 동기**: 같은 채널의 출력 간 재생 위치 편차 ±100ms 이내 유지. 나란히 붙인 화면은 OS 미러링 권장 (§3.7).

**권장 구성표 (2단계에서 실측 후 확정 — 아래는 설계 가정치)**

부하의 단위는 채널이 아니라 **출력**입니다. 채널이 1개여도 모니터 3대에 미러하면 출력 3개 = 디코딩 3개입니다.

| 하드웨어 등급 | 1080p60 출력 | 1080p30 출력 |
|---|---|---|
| 상급 (Apple Silicon Pro/Max, RTX 4070+) | 4~6 | 6~8 |
| 중급 (M시리즈 기본, RTX 3060) | 3~4 | 4~6 |
| 하급 (내장 GPU) | 1~2 | 2~3 |

> 이 표는 **검증 대상이지 약속이 아닙니다.** 2단계 완료 기준에 실측이 포함됩니다.
>
> 같은 화면을 여러 모니터에 띄우는 경우는 **OS 디스플레이 미러링**을 쓰면 출력 1개로 처리되어 이 표의 제약을 받지 않습니다.

**모니터 4대 구성의 현실적 판단** — 상한인 4대를 앱 미러로 채우면 1080p60에서도 상급 하드웨어가 필요합니다. 따라서 4대 구성의 기본 권장은 다음과 같습니다.

| 목적 | 권장 방식 | 출력 수 |
|---|---|---|
| 4대에 **같은 화면** | OS 디스플레이 미러링 | 1 |
| 4대에 **같은 편성, 다른 해상도·비율** | 앱 미러 (스케일 모드 개별 지정) | 4 |
| 4대에 **각각 다른 편성** | 채널 4개 | 4 |

### 6.3 환경 요구사항

- **호환성**: OBS 28 이상, vMix 26 이상. macOS 12+, Windows 10+. **모니터 직출력만 쓰는 경우 OBS·vMix는 불필요.**
- **모니터 직출력 시**: 출력할 모니터가 실제로 연결돼 있어야 함. **최대 4대.** 연결 해제 시 해당 출력만 중단되고 재연결 시 자동 복귀.
- **GPU 하드웨어 디코딩 필수** — 특히 다채널.
- **2채널 이상 오디오 분리 시**: 가상 오디오 드라이버 설치 필요 (BlackHole / VB-Cable).
- **네트워크**: 클라우드 소스 사용 시 대역폭이 (**출력 수** × 재생 비트레이트)를 상회해야 함. 미러 출력도 각자 스트림을 받으므로 그만큼 곱해진다. NDI 사용 시 LAN 대역폭을 별도로 확보해야 한다.

## 7. 일정 (단계별 범위)

| 단계 | 목표 | 산출물 | 완료 기준 |
|------|------|--------|-----------|
| **1. 기획·설계** | 범위 확정 | 기획서 확정, 화면 설계, 데이터 모델 | 본 문서 승인 |
| **2. MVP** | "편성한 게 검은 화면 없이 나간다" | 소스 어댑터(로컬·폴더·CF·Bunny) + 라이브러리 + 채널 1개 + 출력 2종(모니터·창 캡처) + 수동 런다운 + A/B 엔진 + **로고 대기 화면** + **편성 화면(§4.3) 기본형** | **모니터 직출력·OBS 창 캡처 양쪽으로 1080p 1시간 무결절 재생** + **하드웨어 한계 실측** + **1,000개 항목 드래그 반응성 실측** |
| **3. 다채널 · 다중 출력 · 오디오** | 동시 운영 성립 | 채널 매니저, 출력 매니저(모니터 감지·스케일 모드·동기 보정·4대 상한), 출력별 워치독, 오디오 sink 라우팅, 대시보드 | **3채널 동시 송출** + **1채널을 모니터 4대에 미러(1080p)** + 오디오 분리·단일화 확인 + **출력 1개 강제 종료 시 나머지 무영향** |
| **4. 유튜브 통합** | 본인 채널 연동 | OAuth, 재생목록 동기화, IFrame 재생 | 본인 재생목록 편성·재생 |
| **5. 자동화** | 무인 운영 | 자동 편성(버튼 하나), 고정 시각 마커 3종, 필러 자동 선정, 장애 복구, 운영 콘솔, 명령 팔레트 | **다채널 24시간 무인 연속 송출 성공** |
| **6. 스위처 연동 · (조건부) NDI** | 방송 워크플로 통합 | OBS WebSocket, vMix API, 재생 이력. **NDI는 필요할 때만** | 씬 자동 전환 동작. NDI 착수 시 vMix 수신 확인 |

**NDI의 지위 변화** — v1.1에서 4K + 다채널 때문에 "6단계 필수"로 승격했으나, **4K가 전면 보류되면서(§3.7) 승격 근거가 사라져 다시 조건부가 됐습니다.** 1080p 창 4개는 고해상도 모니터 한 대에 배치할 수 있어 화면 공간 문제가 크지 않습니다. NDI는 **채널·출력이 늘어 화면 공간이 실제로 부족해질 때** 착수합니다.

**변경점 (v1.1 대비)**: 모니터 직출력을 **2단계 MVP에 포함**했습니다. Electron이 이미 하는 일(지정 모니터 전체화면)이라 추가 비용이 작고, 오히려 **OBS 없이도 결과를 확인할 수 있어 A/B 엔진 검증이 빨라집니다.** 다중 출력·스케일 모드·동기 보정은 3단계로 묶었습니다.

**2·3·5단계가 이 제품의 성패를 가릅니다.**

## 10. 열린 질문

### 확정됨 (2026-08-27)

- [x] **동시 운영 채널 수** → **다채널 지원.** 상한은 강제하지 않고 하드웨어 실측 기반 권장 구성표 제공
- [x] **오디오 라우팅** → **두 방식 모두 지원.** 시스템 기본(단일 채널용) + 전용 장치(다채널용). 가상 드라이버는 사용자 설치
- [x] **출력 해상도** → **1080p 기본.** **4K는 전면 보류**하며 지원 해상도에서 제외한다. 개발·검증·권장 구성 전부 1080p 기준 (§1.4, §3.7)
- [x] **NDI 우선순위** → **조건부.** 4K 보류로 승격 근거가 사라짐. 채널·출력이 늘어 화면 공간이 부족해질 때만 착수
- [x] **Cloudflare / Bunny** → **둘 다 지원.** `mirrorOf`로 묶어 CDN 폴백에 활용
- [x] **필러** → **자동 선정.** 로컬 항목 한정 + 길이 적합성 + 최근 재생 회피 (§3.6)
- [x] **유튜브 범위** → **본인 채널 한정.** OAuth 인증, 임의 URL 입력 미구현
- [x] **최종 출력 대상** → **선택 가능.** 스위처 공급(창 캡처·NDI)과 모니터 직출력 중 선택하며, 한 채널이 둘을 동시에 가질 수 있음
- [x] **다중 모니터 출력** → **지원.** 한 채널을 여러 모니터에 미러. 모니터별 해상도 자동 감지 + 스케일 모드 개별 설정, 오디오는 출력 하나만 활성
- [x] **모니터 출력 규모** → **한 PC에 최대 4대.** 설계 상한이자 성능 검증 기준. 같은 화면 4대는 OS 미러링 권장 (§3.7)
- [x] **편성 공백 시 화면** → **로고 대기 화면.** 검은 화면은 어떤 장애 상황에도 표시하지 않음 (§3.9)
- [x] **편성 화면 구조** → **리스트 우선 + 타임라인 리본 보조.** 타임라인을 주 편집 화면으로 쓰지 않음 (§4.3.1)
- [x] **고정 시각 처리** → **Hard / Soft / Not Before 3종 마커.** 기존 `overflowPolicy`를 대체 (§3.5)
- [x] **편성 모델** → **3단 파이프라인.** 편성 블록(수동) → 자동 채움(버튼 하나) → 런다운 생성 (§3.5)
- [x] **블록 지정 항목** → 소스 그룹 · 기간 · **요일 복수** · **시간대 복수** · 재생 순서 · 시간 맞춤 (§3.5.1)
- [x] **자동 채움** → 블록 없는 나머지 전 시간을 지정 소스 그룹으로 채워 24시간 완성 (§3.5.2)
- [x] **블록 시작 시각** → **Hard 마커 자동 부여.** "10시 특강"이 정시에 시작하지 않으면 블록의 의미가 없음
- [x] **플레이아웃 방식** → **렌더 + 인코딩 유지.** 가상 라이브(매니페스트 스플라이싱)는 유튜브 소스·오버레이·카메라 합성을 잃으므로 미채택 (부록 C)

## 부록 C: 시청자 전송(딜리버리) 검토 (2026-08-27)

### C.1 배경

"유튜브 라이브에 의존하지 않고 1000명 동시 시청 24시간 채널을 운영하려면?"에 대한 검토입니다. **전송 인프라는 이 제품의 범위 밖(§1.4)이지만, 어떤 방식을 택하느냐가 소스 설계와 아키텍처를 근본적으로 바꾸므로** 결정 기록으로 남깁니다.

> **현재 결정: 기본 전송처는 YouTube Live입니다.** 전송비가 0원이고 도달이 가장 넓기 때문입니다. 아래 내용은 **자체 전송이 필요해질 때를 위한 사전 검토**이며, 지금 착수하는 작업이 아닙니다.
>
> 자체 전송을 검토하게 되는 계기는 대개 셋입니다 — ① 채널 정지·수익화 제한 등 플랫폼 리스크가 현실화될 때 ② 접근 권한 제어(유료·회원 전용)가 필요해질 때 ③ 광고·브랜딩을 완전히 통제해야 할 때.

**용어 주의**: 여기서 다루는 "유튜브"는 **시청자에게 내보내는 출구**입니다. §6.1의 "유튜브는 본인 채널 콘텐츠만"은 **가져오는 소스**에 대한 정책이며 별개의 사안입니다.

### C.2 두 가지 방식

| | **A. 렌더 + 인코딩** (현재 설계) | **B. 가상 라이브** (매니페스트 스플라이싱) |
|---|---|---|
| 구조 | Live Player 렌더 → OBS/vMix 인코딩 → RTMP | 편성표 → 미리 만든 HLS 세그먼트 → 계산된 m3u8 |
| 런타임 인코딩 | 24시간 필요 (인코더 1대) | 없음 |
| 사전 작업 | 없음 | **전 자산을 동일 코덱·해상도·GOP로 재인코딩** |
| 오버레이·자막 | 실시간 가능 | 미리 구워 넣어야 함 |
| 실시간 카메라 합성 | 가능 | 불가 |
| **유튜브 소스** | **사용 가능** | **불가** — 다운로드·재호스팅이 ToS 위반 |
| 소스 종류 | 6종 전부 | 3종으로 축소 (로컬·폴더·업로드분) |
| CDN 전송량 | 동일 | 동일 |

### C.3 비용 실측 (2026-08-27 확인)

**전제**: 720p / 2Mbps / 동시 1000명 / 24시간 / 30일 = **648 TB/월**

| 전송처 | 단가 | 월 비용 |
|---|---|---|
| **Bunny CDN Volume** | $0.005/GB (첫 500TB), $0.004/GB (~1PB) | **$3,092** |
| **Bunny Stream** | $0.005/GB · 인코딩·플레이어 무료 | **≈ $3,092** |
| **Cloudflare Stream** | $1 / 1,000분 전송 (43,200,000 viewer-min) | **$43,200** |

동시 시청자에 따른 실제 비용 (Bunny 기준, 2Mbps)

| 평균 동접 | 월 트래픽 | 월 비용 | 원화 (≈1,380원/$) |
|---|---|---|---|
| 100명 | 64.8 TB | $324 | 약 45만원 |
| 300명 | 194.4 TB | $972 | 약 134만원 |
| 500명 | 324 TB | $1,620 | 약 224만원 |
| 1000명 | 648 TB | $3,092 | 약 427만원 |

> **최고 동접 1000명 ≠ 평균 동접 1000명.** 위 최악 수치는 "한 명도 빠지지 않고 30일간 계속 시청"이라는 비현실적 조건입니다. 실제 비용은 평균 동접으로 계산해야 합니다.

### C.4 핵심 판단 — 절감의 원인은 아키텍처가 아니라 벤더다

두 개의 서로 다른 결정을 분리해야 합니다.

| 결정 | 차이 |
|---|---|
| **① 전송처** — Cloudflare Stream vs Bunny | **연 $482,000** ← 돈은 전부 여기 |
| **② 플레이아웃** — 렌더+인코딩 vs 가상 라이브 | **서버 1대** (월 $50~150) |

**CDN 전송 바이트는 A·B가 동일합니다.** 가상 라이브가 아끼는 것은 인코더 한 대뿐이며, 14배 절감은 전적으로 벤더 선택에서 나옵니다.

> **결론: 방식 A(렌더+인코딩)를 유지하고, 전송처로 Bunny를 쓴다.** 기획서가 이미 Bunny Stream을 채택한 것은 CDN 폴백(§3.1) 때문이었으나, 비용 측면에서도 같은 답이 나왔습니다.

### C.5 가상 라이브를 채택하지 않는 이유

1. **유튜브 소스가 사라진다** — 6종 소스 설계(§3.1)의 전제가 무너진다
2. **오버레이·자막·카메라 합성이 불가능**해져 제품 성격이 달라진다
3. **전 자산 사전 정규화** 비용이 발생한다 (출처 6곳의 코덱·GOP를 하나로 통일)
4. **VOD ↔ 실제 생방송 전환이 어렵다** — 같은 m3u8을 유지하려면 `EXT-X-DISCONTINUITY` 처리·코덱 파라미터 일치·세그먼트 경계 정렬이 필요하고 플레이어마다 반응이 다르다
5. 얻는 것은 서버 한 대 값

**향후 재검토 조건**: 오버레이·카메라·유튜브 소스를 전혀 쓰지 않는 순수 파일 채널이 생기면 그때 가상 라이브를 검토한다.

### C.6 권고 구성

```
Live Player(렌더) → OBS/vMix(인코딩) → RTMP ─┬─→ YouTube Live         (전송비 0원 · 플랫폼 종속)
                                              └─→ MediaMTX 또는 SRS
                                                    → HLS → Bunny CDN  (독립 · 유료)
```

- **1단계 — 유튜브 단독 (현재 결정).** 전송비 0원. Live Player와 OBS만으로 완결된다. 추가 인프라 없음
- **2단계 — 필요해지면 자체 전송을 병행.** OBS는 다중 출력을 지원하고 채널별 스위처 바인딩(§3.3)이 이미 설계에 있으므로, Live Player 쪽 변경 없이 출구만 추가하면 된다
- 유튜브로 **도달**을 얻고, 자체 채널로 **독립성**을 확보한다. 둘은 배타적이지 않다
- 2단계에 필요한 인프라는 작은 VPS 1대(RTMP ingest + HLS 패키징). 1000명이 붙어도 CDN이 전부 흡수하므로 2코어로 충분하다
- **처음부터 1000명을 가정해 짓지 않는다.** 자체 채널의 실제 트래픽을 본 뒤 규모를 정한다

> **이 설계의 이점은 출구를 나중에 바꿔도 Live Player가 그대로라는 점입니다.** 렌더 → OBS까지가 제품이고, 그 뒤는 OBS 설정 문제입니다. 가상 라이브를 택했다면 이런 유연성이 없습니다(C.5).

### C.7 Cloudflare R2 정책 메모

R2는 egress가 무료(저장 $0.015/GB·월)여서 전송 비용이 이론상 0에 가깝습니다. 관련해 흔히 인용되는 "CDN 영상 전송 제한(구 Section 2.8)"은 **2023년 5월에 폐지**되었고, 현행 약관은 Stream·Images·Developer Platform(R2 포함)에 호스팅된 콘텐츠의 CDN 영상 전송을 허용합니다.

다만 약관에 `disproportionate percentage of ... large files` 문구가 남아 있고, 월 648TB 순수 영상은 정확히 그 문구가 겨냥하는 규모입니다. **채널을 R2에 걸기 전에 Cloudflare로부터 서면 확인을 받아야 합니다.** 확인이 되면 비용 측면에서는 1순위가 될 수 있습니다.
