## 1. 개요

### 1.1 한 줄 정의

**Live Player는 흩어져 있는 6종의 영상 소스를 하나의 라이브러리로 묶어 자동·수동으로 편성하고, 그 편성을 무결절로 재생하는 출력창을 OBS·vMix에 공급하는 다채널 플레이아웃 도구다.**

### 1.2 배경 / 문제 정의

유튜브 라이브 채널이나 모니터 송출을 운영할 때, 실제로는 콘텐츠가 여러 곳에 흩어져 있습니다.

- 로컬 하드의 완성본 영상 파일
- 계속 파일이 쌓이는 작업 폴더
- 이미 자기 유튜브 채널에 올려둔 영상과 재생목록
- Cloudflare Stream에 올려둔 영상
- Bunny Stream에 올려둔 영상

지금은 이걸 편성하려면 OBS 미디어 소스를 하나씩 손으로 바꾸거나, 로컬로 전부 내려받아 재인코딩해야 합니다. 24시간 채널이나 장시간 송출은 사실상 사람이 붙어 있어야 하고, **채널을 하나 늘리면 운영 부담이 그대로 두 배가 됩니다.**

**문제의 핵심은 "소스가 여러 곳이라 하나의 편성표로 묶이지 않는다"는 것입니다.**

### 1.3 목표

1. 6종 소스를 **출처와 무관하게 동일하게 다루는 단일 라이브러리**를 제공한다.
2. 시간 블록을 지정하면 **길이를 계산해 자동으로 채우는 편성**과, 순서를 직접 짜는 **수동 편성**을 모두 지원한다.
3. 편성된 내용을 **검은 화면 없이 이어 재생하는 출력창**을 띄운다.
4. **여러 채널을 동시에** 독립 편성·독립 출력한다.
5. 각 출력창이 **OBS·vMix에서 안정적으로 캡처**되어 유튜브 라이브 또는 모니터로 나간다.
6. **무인 24시간 운영**이 가능하도록 실패 시 자동 복구한다.

### 1.4 비목표 (Non-goals)

명시적으로 이번 범위에서 제외합니다.

- **영상 인코딩·트랜스코딩** — 인코딩은 OBS/vMix가 담당. Live Player는 재생과 편성만 한다.
- **직접 RTMP 송출** — 스트리밍 출력은 OBS/vMix에 위임한다. 자체 송출 기능을 만들지 않는다.
- **영상 편집** — 컷 편집, 자막 렌더링, 합성은 다루지 않는다.
- **타인 콘텐츠 재송출** — 본인 소유 채널·계정의 콘텐츠만 등록 대상으로 한다 (§6.1 참조).
- **디지털 사이니지** — 전광판·매장 TV 편성은 기존 CDMB CMS의 영역이며, 여기서 중복 구현하지 않는다.
- **멀티테넌트 SaaS** — 채널은 여러 개지만 **운영자는 한 명**이다. 계정 관리·권한 분리·요금제는 다루지 않는다.

### 1.5 CDMB CMS와의 관계

같은 "영상 + 스케줄 + 재생창" 구조지만 **출력을 누가 받느냐**가 달라서 별개 제품입니다.

| | CDMB CMS | Live Player |
|---|---|---|
| 출력의 최종 소비자 | 디스플레이(전광판·TV) = 종점 | OBS/vMix = 중간 단계 |
| 재생창의 성격 | 최종 화면 | **방송 스위처의 입력 소스** |
| 전환 시 검은 프레임 | 문제되지 않음 | **방송사고** |
| 스케줄 모델 | 요일 × 시간대 그리드(반복 편성) | 런다운(연속 편성, 예상 시작시각) |
| 항목 길이 정보 | 없어도 동작 | **필수** (자동 편성의 전제) |
| 외부 제어 | 서버 → 플레이어 단방향 | 스위처와 **양방향** 상태 동기화 |
| 동시 출력 | 디스플레이 여러 대에 **같은 편성** | 채널마다 **다른 편성** |
| 소스 종류 | 로컬 파일·업로드·유튜브·이미지 | 로컬·폴더·유튜브(채널)·CF Stream·Bunny |
| 배포 형태 | 멀티테넌트 SaaS + 로컬 앱 | 단일 운영자용 로컬 앱 |

**코드는 공유하지 않되, 검증된 설계 원칙은 가져옵니다.**

가져올 개념
- 서버가 진실의 원천(single source of truth), WebSocket 브로드캐스트로 상태 전파
- 미리보기와 실제 출력이 **같은 재생 엔진**을 사용 → 화면 일치 보장
- JSON 파일 스토어 기반의 가벼운 영속성
- Electron 멀티모니터 감지·전체화면 처리

새로 만들 것
- A/B 무결절 재생 엔진
- 런다운형 스케줄 모델
- 소스 어댑터 레이어
- **채널 관리 계층** (독립 편성·독립 출력·독립 오디오)
- OBS·vMix 연동 계층

## 2. 사용자

### 2.1 타깃 사용자

| 유형 | 특징 | 핵심 니즈 |
|------|------|-----------|
| **다채널 운영자** | 유튜브 24시간 라이브를 주제별로 2~4개 채널 운영 | 채널마다 다른 편성이 사람 없이 동시에 돌아가야 함 |
| **1인 채널 운영자** | 유튜브 24시간 라이브(음악·설교·강의 재방송)를 혼자 운영 | 한 번 편성해두면 사람 없이 계속 돌아가야 함 |
| **교회·단체 미디어 담당** | 주중 재방송 채널 + 주일 라이브. OBS는 이미 사용 중 | 기존 OBS 워크플로를 바꾸지 않고 소스만 자동화 |
| **행사·전시 운영자** | 현장 모니터 여러 대에 각각 다른 영상 루프 + 정시 콘텐츠 | 모니터별 다른 편성, 고정 시각 정확도 |

**공통 전제**: OBS 또는 vMix를 이미 쓰고 있으며, 그것을 대체할 생각이 없다.

### 2.2 사용 시나리오

**S1. 24시간 재방송 채널 (자동 편성)**
1. 운영자가 자기 유튜브 채널의 "지난 설교" 재생목록을 라이브러리에 연결한다.
2. 채널 1을 만들고 "매일 00:00~24:00, 이 재생목록을 랜덤 순서로 채움"으로 자동 편성한다.
3. 채널 1 출력창을 띄우고 OBS에서 캡처해 유튜브 라이브를 시작한다.
4. 이후 사람이 개입하지 않아도 매일 편성이 재생성되어 계속 나간다.

**S2. 다채널 동시 운영**
1. 채널 1은 "설교 재방송", 채널 2는 "찬양 음악", 채널 3은 "행사 모니터"로 각각 만든다.
2. 채널마다 해상도·오디오 출력 장치·편성이 다르다.
3. 세 개의 출력창이 동시에 각자의 런다운을 재생한다.
4. 하나가 장애로 재기동돼도 나머지 두 채널은 영향받지 않는다.

**S3. 정시 콘텐츠가 있는 편성 (수동 + 고정시각)**
1. 로컬 폴더의 영상들로 오전 블록을 자동으로 채운다.
2. "10:00 정각에 반드시 이 영상"을 **고정 시각 항목**으로 지정한다.
3. 앞 항목이 10:00을 넘기면 자동으로 트림하거나, 모자라면 필러를 넣어 정시를 맞춘다.

**S4. 현장 대응 (수동 개입)**
1. 송출 중 운영자가 특정 채널에서 "다음 항목 건너뛰기"를 누른다 → 현재 항목이 끝나는 즉시 다음으로 넘어간다.
2. "지금 바로 이 영상"을 누르면 현재 항목을 끊고 즉시 전환한다.
3. 개입이 끝나면 원래 런다운으로 자동 복귀한다. **다른 채널은 영향 없다.**

**S5. 스위처 연동**
1. 채널별로 OBS WebSocket 접속 정보를 등록한다 (같은 OBS의 다른 씬, 또는 서로 다른 OBS 인스턴스).
2. 편성 항목에 "이 항목 재생 시 OBS 씬을 `LIVE-VIDEO`로 전환" 규칙을 건다.
3. 편성이 끝나는 시각에 자동으로 `대기화면` 씬으로 되돌린다.

### 3.1 소스 어댑터 (P0)

모든 소스는 **하나의 공통 항목(Item)으로 정규화**됩니다. 편성기와 재생 엔진은 출처를 모릅니다.

```
Item {
  id           고유 ID
  sourceType   local | folder | youtube | youtube_playlist | cloudflare | bunny
  title        표시 이름
  durationMs   길이 (필수 — 자동 편성의 전제)
  thumbnail    썸네일 URL / 로컬 경로
  playback     재생 방식별 참조
  maxResolution 원본 최대 해상도 (4K 채널 편성 시 판단 근거)
  isLocal      로컬에서 즉시 재생 가능 여부 (필러 후보 자격)
  mirrorOf     동일 콘텐츠의 다른 소스 ID (CF ↔ Bunny 폴백용)
  status       ready | resolving | error
  lastCheckedAt
}
```

| 소스 | 등록 방법 | 길이(duration) 획득 | 재생 방식 |
|------|-----------|---------------------|-----------|
| **로컬 파일** | 파일 선택 / 드래그앤드롭 | ffprobe | 로컬 서버가 스트리밍(Range 지원) → `<video>` |
| **지정 폴더** | 폴더 지정 후 스캔·감시 | ffprobe (스캔 시 일괄) | 위와 동일 |
| **유튜브 동영상** | 본인 채널 목록에서 선택 | YouTube Data API `contentDetails.duration` | IFrame Player API |
| **유튜브 재생목록** | 본인 채널 재생목록 선택 | 재생목록 항목 일괄 조회 | 항목별 IFrame Player API |
| **Cloudflare Stream** | 계정 연결 후 목록 동기화 | Stream API `duration` | HLS 매니페스트 → hls.js |
| **Bunny Stream** | 라이브러리 연결 후 목록 동기화 | Video API `length` | HLS 플레이리스트 → hls.js |

**폴더 소스는 "동적 풀"입니다.** 개별 항목이 아니라 폴더 자체를 편성에 걸 수 있고, 파일이 추가되면 다음 편성 생성 시 자동 반영됩니다. 유튜브 재생목록도 같은 성격입니다.

**Cloudflare / Bunny 병행 사용** — 둘 다 HLS로 나오므로 재생 경로는 하나(hls.js)로 통합되고, 어댑터만 두 벌입니다. 병행의 실익은 두 가지입니다.

1. 기존에 어디에 올려뒀든 그대로 쓸 수 있다 (이전 작업 불필요)
2. 같은 콘텐츠를 양쪽에 두면 `mirrorOf`로 묶어 **CDN 장애 시 자동 폴백**이 된다

### 3.2 무결절 재생 엔진 (P0)

**이 제품에서 가장 중요한 부분이며, CMS에서 가져올 수 없는 부분입니다.**

동작 원리
1. 출력창은 비디오 레이어를 **두 개(A/B)** 갖는다.
2. 현재 A가 재생 중이면, 다음 항목을 **B에 미리 로드하고 첫 프레임까지 디코드**해 둔다.
3. A의 종료 지점에서 B를 표시하고 A를 숨긴다 → 검은 프레임이 생기지 않는다.
4. 다음 항목을 A에 다시 프리로드한다. 이후 반복.

프리로드 시작 시점은 소스별로 다르게 잡습니다.

| 소스 | 프리로드 시작 | 근거 |
|------|---------------|------|
| 로컬 / 폴더 | 종료 10초 전 | 디스크 읽기, 거의 즉시 |
| Cloudflare / Bunny | 종료 20초 전 | HLS 세그먼트 버퍼 확보 |
| 유튜브 | 종료 30초 전 | 임베드 초기화 + 버퍼링 여유 |

**다채널에서의 디코더 예산** — 채널당 A/B 두 레이어이므로 최악의 경우 채널 수의 2배가 동시 디코딩됩니다. 다만 B는 프리로드 구간(10~30초)에만 활성이므로 **평시에는 채널당 1개, 전환 직전에만 2개**입니다. 채널별 프리로드 시작 시점을 의도적으로 어긋나게 배치해 동시 피크를 분산시킵니다.

**유튜브의 한계는 설계에 명시합니다.** IFrame 임베드는 앱이 디코딩을 직접 통제하지 못하고, 광고 삽입 여부·버퍼링 타이밍도 통제 밖입니다. 본인 채널 콘텐츠라도 마찬가지입니다. 따라서 유튜브 항목의 무결절 전환은 **최선 노력(best-effort)**이며 완전 보장 대상이 아닙니다.

> **권장 운영 방식**: 온에어가 중요한 채널은 본인 유튜브 콘텐츠를 Cloudflare Stream 또는 Bunny Stream에 미러링해 두고 그쪽을 편성한다. 유튜브 소스는 아카이브 탐색·프리뷰·비중요 편성용으로 쓴다. — **Cloudflare/Bunny를 백본으로, 유튜브를 보조로 두는 것이 이 제품의 기본 권장 구성이다.**

### 3.3 채널 (P0)

**채널은 "독립된 하나의 송출 라인"입니다.** 라이브러리는 전 채널이 공유하고, 그 외 모든 것은 채널마다 독립입니다.

```
Channel {
  id, name
  resolution        3840x2160 | 1920x1080 | 1080x1920 | 2160x3840 | custom
  outputMode        window | ndi          출력 방식
  displayId         window 모드에서 사용할 모니터
  audioMode         system | device        §3.4
  audioDeviceId     device 모드에서 사용할 출력 장치
  rundownId         현재 편성
  fillerPolicy      필러 자동 선정 규칙 (§3.6)
  switcher          { type: obs|vmix, host, port, auth, sceneMap }
  state             stopped | running | recovering
}
```

원칙
- **격리**: 한 채널의 장애·재기동이 다른 채널에 영향을 주지 않는다. 채널마다 독립된 출력창 프로세스와 워치독을 갖는다.
- **공유**: 라이브러리·소스 자격증명·메타데이터 캐시는 전 채널이 공유한다. 같은 영상을 두 채널이 동시에 편성해도 문제없다.
- **독립 편성**: 채널마다 다른 런다운. 같은 런다운을 여러 채널에 복사할 수는 있다.

**채널 수 상한은 하드웨어가 결정합니다.** 앱은 상한을 강제하지 않되, **채널 추가 시 예상 디코더 부하와 현재 여유를 표시하고 경고**합니다. 실제 한계치는 2단계에서 실측해 권장 구성표로 문서화합니다 (§6.2).

### 3.4 오디오 라우팅 (P0)

**두 방식을 모두 지원하되, 다채널에서는 사실상 하나만 유효합니다.**

| 모드 | 동작 | 적합한 경우 | 한계 |
|------|------|-------------|------|
| **시스템 기본** | OS 기본 출력으로 재생 → OBS "데스크톱 오디오"로 캡처 | **단일 채널**. 설정 없이 바로 동작 | 여러 채널이 한 버스에 섞인다. 채널 분리 불가 |
| **전용 장치** | 채널마다 다른 출력 장치로 라우팅 → OBS가 장치별로 개별 캡처 | **다채널**. 채널별 볼륨·믹싱 독립 | 가상 오디오 장치 설치 필요 |

구현: Electron(Chromium)의 `setSinkId`로 채널별 출력 장치를 지정합니다. A/B 두 레이어 모두 같은 sink로 설정해야 전환 시 소리가 끊기지 않습니다.

전용 장치 모드에 필요한 가상 오디오 드라이버
- **macOS**: BlackHole (다중 채널이면 인스턴스 여러 개, 또는 16ch 버전을 채널별 페어로 분배)
- **Windows**: VB-Cable (다중 인스턴스) 또는 VoiceMeeter

앱은 드라이버를 설치하지 않습니다. 대신 **설정 화면에서 사용 가능한 출력 장치를 나열하고, 채널 수보다 장치가 부족하면 경고와 함께 설치 안내를 표시**합니다.

> **정책**: 2채널 이상을 만들면 앱이 전용 장치 모드를 권장하고, 시스템 기본 모드를 유지할 경우 "채널 오디오가 섞입니다"라고 명시적으로 경고한다.

### 3.5 런다운 편성 (P0 / P1)

사이니지의 "요일 × 시간대 그리드"가 아니라, **항목이 등을 맞대고 흘러가는 런다운**입니다.

```
Rundown {
  id, name, channelId, date
  items: [
    { itemId, order,
      startAtEstimated,   자동 계산된 예상 시작 시각
      startAtFixed,       고정 시각 (선택) — 있으면 정시 강제
      overflowPolicy,     trim | filler   고정시각 충돌 시 처리
      trimIn, trimOut,    구간 재생 (선택)
      onAirRules }        스위처 연동 규칙 (선택)
  ]
}
```

- **예상 시작 시각 자동 계산**: 각 항목의 `durationMs`를 누적해 계산. 항목을 넣거나 빼면 이후 전부 재계산.
- **고정 시각 항목**: 지정 시각에 반드시 시작. 앞 항목이 넘치면 트림, 모자라면 필러 삽입 — `overflowPolicy`로 항목별 선택.
- **자동 편성 (P1)**: "시간 블록 + 소스 풀 + 채움 방식(순차/랜덤/미방영 우선)" → 길이를 계산해 블록을 채운다. 남는 자투리는 필러로 메운다.
- **반복 편성**: 매일/매주 같은 규칙으로 런다운을 자동 재생성. 채널마다 다른 규칙.
- **해상도 적합성 경고**: 4K 채널에 1080p 원본을 배치하면 업스케일 경고를 표시한다(차단하지는 않음).

### 3.6 필러 자동 선정 (P1)

**필러는 편성 공백과 장애 상황에서 대신 나가는 예비 콘텐츠**이며, 운영자가 매번 지정하지 않고 자동 선택합니다.

선정 규칙 (우선순위 순)

1. **로컬 재생 가능한 항목만** (`isLocal = true`) — 필러가 필요한 상황은 대개 네트워크 장애다. 클라우드 필러는 정작 필요할 때 못 쓴다.
2. **길이 적합성** — 메워야 할 공백에 가장 잘 맞는 길이. 넘치면 트림 가능한 항목 우선.
3. **최근 재생 회피** — 최근 N시간 내 나간 항목은 후보에서 제외 (같은 필러 반복 방지).
4. **필러 풀 제한** — 운영자가 태그나 폴더로 "필러 후보 풀"을 지정했으면 그 안에서만 고른다. 미지정 시 라이브러리 전체의 로컬 항목.

```
FillerPolicy {
  poolTag         후보 풀 (미지정 시 로컬 전체)
  avoidRecentHours 기본 6시간
  allowTrim       공백에 맞춰 잘라 쓸지 여부
  lastResort      모든 조건 실패 시 쓸 고정 루프 클립 (선택)
}
```

**사전 캐시**: 앱은 필러 후보 중 상위 몇 개를 항상 프리로드 가능 상태로 유지해, 장애 발생 시 대기 없이 즉시 전환합니다.

**최후 수단 체인**: 필러 후보 없음 → `lastResort` 클립 → 대기 화면(로고/검정). 어느 단계든 검은 화면이 나가면 이력에 기록하고 경고합니다.

### 3.7 출력창 (P0)

OBS·vMix가 **깨끗하게 캡처할 수 있는 창**이 되는 것이 유일한 목적입니다.

- 프레임리스, 지정 해상도로 픽셀 고정. 창 크기 변경 불가.
- UI 크롬·커서·툴팁·알림 없음. 배경은 순수 검정.
- 지정 모니터로 이동, 필요 시 전체화면.
- 채널별 오디오 출력 장치 적용 (§3.4).
- 크래시 시 자동 재기동 + 런다운 현재 지점 복귀.

지원 해상도: **3840×2160(4K)**, 1920×1080, 1080×1920(세로), 2160×3840(4K 세로), 사용자 지정.

**출력 방식은 두 가지이며, 4K·다채널에서는 NDI가 사실상 필수입니다.**

| 방식 | 동작 | 장점 | 제약 |
|------|------|------|------|
| **창 캡처** (1차) | 출력창을 OBS 창 캡처 / vMix Desktop Capture로 가져감 | 추가 설치 불필요, 즉시 사용 | **창 픽셀 수만큼의 실제 디스플레이 표면이 필요.** 4K 출력엔 4K 디스플레이(또는 더미 HDMI/EDID 에뮬레이터, macOS 가상 디스플레이)가 있어야 함. 다채널이면 창들이 화면을 나눠 써야 함 |
| **NDI 출력** (P2) | 렌더 결과를 NDI 스트림으로 직접 송출 | **디스플레이 불필요.** 4K·다채널이 자연스럽게 해결. vMix와 궁합 최적 | NDI 런타임 필요, 네트워크 대역폭(4K는 상당함) |

**OBS 브라우저 소스는 1차 지원 대상에서 제외합니다** — 내장 CEF의 유튜브 임베드·DRM 처리 문제 때문입니다.

### 3.8 장애 복구 (P1)

무인 24시간 운영이 목표이므로 실패를 전제로 설계합니다. **모든 복구는 채널 단위로 격리됩니다.**

| 상황 | 대응 |
|------|------|
| 다음 항목 프리로드 실패 | 즉시 그 다음 항목으로 스킵, 실패 기록 |
| CDN 응답 없음 (CF 또는 Bunny) | `mirrorOf`로 묶인 반대편 소스로 자동 전환 |
| 스킵할 항목도 없음 | **자동 선정된 필러** 재생 (§3.6) |
| 필러도 없음 | `lastResort` 클립 → 대기 화면(로고/검정) |
| 네트워크 끊김 | 로컬 캐시 항목으로 자동 전환 |
| 출력창 응답 없음 | 해당 채널 워치독이 감지 → 그 채널만 재기동 → 런다운 현재 지점 복귀 |
| 서버 프로세스 종료 | 자동 재시작 후 running 상태였던 채널 전부 복구 |
| 디코더 자원 부족 | 우선순위 낮은 채널의 프리로드를 지연시켜 피크 회피, 경고 표시 |

### 4.2 핵심 플로우

```
[라이브러리] 소스 연결 → 동기화 → 길이·해상도 조회 완료(ready)
      ↓
[채널 설정] 채널 생성 → 해상도·출력방식·오디오 장치 지정
      ↓
[편성] 채널별 자동 채움 또는 드래그 배치 → 예상 시작시각 확정 → 저장
      ↓
[채널 대시보드] 채널 송출 시작 → 출력창 열림 (채널마다 독립)
      ↓
[출력창] A/B 엔진이 런다운을 순서대로 무결절 재생
      ↓
[OBS/vMix] 창 캡처 또는 NDI → 인코딩 → 유튜브 라이브 / 모니터
```

미리보기와 출력창은 **같은 재생 엔진**을 씁니다(CMS에서 검증된 원칙). 콘솔에서 보는 화면이 곧 나가는 화면입니다.

## 5. 기술 구성

### 5.1 플랫폼

**Electron 데스크톱 앱 (macOS · Windows)**

웹앱이 아니라 데스크톱 앱이어야 하는 이유:
- 출력창의 크기·위치·크롬을 픽셀 단위로 통제해야 캡처가 안정적이다
- 채널별 오디오 출력 장치 라우팅이 필요하다
- 로컬 폴더 접근·감시가 필요하다
- 멀티모니터 지정 출력이 필요하다
- 24시간 무인 운영을 위한 워치독·자동 재기동이 필요하다
- NDI 출력에는 네이티브 바인딩이 필요하다

### 5.2 기술 스택

| 영역 | 선택 | 근거 |
|------|------|------|
| 셸 | Electron | CMS에서 검증된 배포·서명·업데이트 파이프라인 재사용 |
| 서버 | Node.js + Express | 단일 프로세스, 로컬 미디어 Range 스트리밍 |
| 실시간 | ws (WebSocket) | 서버 → 채널별 출력창·콘솔 상태 브로드캐스트 |
| 영속성 | JSON 파일 스토어 | 라이브러리·채널·런다운 규모에 충분. DB 도입은 과함 |
| HLS 재생 | hls.js | Cloudflare·Bunny 공통 |
| 유튜브 재생 | YouTube IFrame Player API | 대안 없음 |
| 오디오 라우팅 | Chromium `setSinkId` | 채널별 출력 장치 지정 |
| 메타데이터 | ffprobe (로컬), 각 서비스 REST API | 길이·해상도 정확도 확보 |
| OBS 연동 | obs-websocket-js (v5) | 표준 |
| vMix 연동 | HTTP API (:8088) / TCP API (:8099) | 표준 |
| NDI 출력 | NDI SDK 네이티브 바인딩 | 4K·다채널 해법 |
| 빌드·배포 | electron-builder | CMS와 동일 |

### 5.3 아키텍처

```
┌──────────────────────────────────────────────────────────┐
│ Electron 메인 프로세스                                     │
│  ├ 로컬 서버 (Express + ws)                               │
│  │   ├ 소스 어댑터 레이어   ← 6종 소스 정규화               │
│  │   ├ 라이브러리 스토어    ← 전 채널 공유                  │
│  │   ├ 채널 매니저          ← 채널 생명주기·자원 예산       │
│  │   ├ 런다운 스케줄러 ×N   ← 채널마다 독립 인스턴스        │
│  │   ├ 필러 선정기          ← 로컬 후보 사전 캐시           │
│  │   ├ 미디어 스트리머      ← 로컬 파일 Range 서빙          │
│  │   └ 스위처 브리지        ← OBS WS / vMix API (채널별)   │
│  ├ 출력창 관리 ×N (해상도·모니터·오디오 sink·워치독)         │
│  └ 폴더 감시                                              │
└──────┬────────────────────────────┬──────────────────────┘
       │ WebSocket                  │ WebSocket (채널별)
┌──────▼──────────┐    ┌────────────▼─────────────────────┐
│ 관리 UI          │    │ 출력창 #1   출력창 #2   출력창 #3 │
│ 대시보드/라이브   │    │ A/B 엔진    A/B 엔진    A/B 엔진 │
│ 러리/편성/콘솔    │    │ UI 없음     UI 없음     UI 없음  │
│ 같은 엔진 미리보기 │    └──────┬──────────┬─────────┬─────┘
└─────────────────┘           │ 창캡처 또는 NDI       │
                       ┌──────▼──────────────────────▼────┐
                       │        OBS / vMix                 │
                       └──────────────┬───────────────────┘
                                      │ RTMP / HDMI
                       ┌──────────────▼───────────────────┐
                       │ 유튜브 라이브 (채널별) / 모니터     │
                       └──────────────────────────────────┘
```

**서버가 진실의 원천**입니다. 매초 각 채널의 현재 시각을 기준으로 "이 채널이 지금 무엇을 재생해야 하는가"를 계산해 해당 출력창과 콘솔에 브로드캐스트합니다. 출력창은 판단하지 않고 지시받은 것을 재생합니다 — CMS에서 검증된 구조를 채널 수만큼 복제한 형태입니다.

**채널 매니저**가 추가된 계층입니다. 채널 생명주기(생성·시작·정지·재기동)를 관리하고, 디코더·대역폭 예산을 추적해 프리로드 타이밍을 채널 간에 분산시킵니다.

## 6. 제약 조건

### 6.1 콘텐츠 정책 — 본인 소유 콘텐츠 한정

**Live Player는 운영자 본인이 소유·관리하는 채널·계정의 콘텐츠만 등록 대상으로 합니다.**

- 유튜브 소스는 **OAuth로 인증한 본인 채널의 영상·재생목록만** 등록 가능하도록 구현한다. 임의의 유튜브 URL 붙여넣기는 허용하지 않는다.
- Cloudflare Stream·Bunny Stream은 운영자 본인 계정의 라이브러리만 연결한다.
- 로컬 파일·폴더는 운영자 책임 영역이다.

이 제약은 저작권과 각 서비스 이용약관 준수를 위한 것이며, **기능 편의를 이유로 완화하지 않습니다.**

### 6.2 성능 · 자원

- **전환 품질**: 항목 전환 시 검은 프레임 0 (유튜브 소스 제외 — best-effort).
- **정시성**: 고정 시각 항목의 시작 오차 ±1초 이내. 채널 수와 무관.
- **연속 운영**: 72시간 무중단 재생 시 메모리 누수로 인한 성능 저하 없을 것.
- **채널 수**: 앱은 상한을 강제하지 않는다. 대신 채널 추가 시 예상 부하를 표시하고, **2단계에서 실측한 권장 구성표**를 제공한다.

**권장 구성표 (2단계에서 실측 후 확정 — 아래는 설계 가정치)**

| 하드웨어 등급 | 1080p60 채널 | 4K30 채널 | 혼합 예시 |
|---|---|---|---|
| 상급 (Apple Silicon Pro/Max, RTX 4070+) | 4~6 | 2 | 4K×1 + 1080p×3 |
| 중급 (M시리즈 기본, RTX 3060) | 3~4 | 1 | 4K×1 + 1080p×1 |
| 하급 (내장 GPU) | 1~2 | 0~1 | 1080p×2 |

> 이 표는 **검증 대상이지 약속이 아닙니다.** 2단계 완료 기준에 실측이 포함됩니다.

### 6.3 환경 요구사항

- **호환성**: OBS 28 이상, vMix 26 이상. macOS 12+, Windows 10+.
- **GPU 하드웨어 디코딩 필수** — 특히 4K·다채널.
- **4K 창 캡처 시**: 4K 디스플레이, 더미 HDMI(EDID 에뮬레이터), 또는 macOS 가상 디스플레이가 필요. 없으면 NDI 출력을 사용.
- **2채널 이상 오디오 분리 시**: 가상 오디오 드라이버 설치 필요 (BlackHole / VB-Cable).
- **네트워크**: 클라우드 소스 사용 시 대역폭이 (채널 수 × 재생 비트레이트)를 상회해야 함. NDI 사용 시 4K는 상당한 LAN 대역폭 필요.

## 7. 일정 (단계별 범위)

| 단계 | 목표 | 산출물 | 완료 기준 |
|------|------|--------|-----------|
| **1. 기획·설계** | 범위 확정 | 기획서 확정, 화면 설계, 데이터 모델 | 본 문서 승인 |
| **2. MVP** | "편성한 게 검은 화면 없이 나간다" | 소스 어댑터(로컬·폴더·CF·Bunny) + 라이브러리 + 채널 1개 + 수동 런다운 + A/B 엔진 + 출력창 | OBS 창 캡처로 **1080p 1시간 무결절 재생** + **4K 캡처 경로 검증** + **하드웨어 한계 실측** |
| **3. 다채널 · 오디오** | 동시 운영 성립 | 채널 매니저, 채널별 출력창·워치독, 오디오 sink 라우팅, 대시보드 | **3채널 동시 송출, 오디오 분리 확인, 1채널 강제 종료 시 나머지 무영향** |
| **4. 유튜브 통합** | 본인 채널 연동 | OAuth, 재생목록 동기화, IFrame 재생 | 본인 재생목록 편성·재생 |
| **5. 자동화** | 무인 운영 | 자동 편성, 고정 시각, 필러 자동 선정, 장애 복구, 운영 콘솔 | **다채널 24시간 무인 연속 송출 성공** |
| **6. NDI · 스위처 연동** | 4K·다채널 완성 | NDI 출력, OBS WebSocket, vMix API, 재생 이력 | **4K 채널을 NDI로 vMix 수신**, 씬 자동 전환 동작 |

**변경점 (v1.0 대비)**: 다채널·오디오를 3단계로 신설하고, NDI를 최종 선택 기능에서 **6단계 필수 항목으로 승격**했습니다. 4K 창 캡처는 디스플레이 표면 제약이 있고 다채널은 화면 공간을 나눠 써야 하므로, 두 결정이 겹치면 NDI가 선택이 아니라 전제가 됩니다.

**2·3·5단계가 이 제품의 성패를 가릅니다.**
