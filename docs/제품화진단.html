팔기 전에 막아야 할 구멍

다섯 개 모두 “기능이 모자라서”가 아니라 “고객 환경에서 무너져서”입니다. 그래서 기능 추가보다 먼저입니다.

01

ffmpeg를 시스템에서 찾고 있습니다

치명
server/probe.js — const { stdout } = await run('which', ['ffprobe']);

고객 PC에는 ffmpeg가 없습니다. 영상 길이를 읽지 못하므로 라이브러리 스캔이 통째로 실패합니다. 첫 실행에서 아무것도 못 합니다.

번들해야 하는데 여기에 법적 문제가 붙습니다. ffmpeg 빌드에 따라 LGPL이냐 GPL이냐가 갈리고, GPL 빌드를 번들하면 제품 전체를 GPL로 공개해야 할 수 있습니다.

조치 — LGPL 빌드를 골라 번들하고, 소스 제공 고지와 라이선스 문구를 앱에 넣는다. 개발보다 컴플라이언스 확인이 더 오래 걸린다.
02

24/7을 파는데 40분까지만 검증했습니다

치명

제품명이 24/7 Broadcast Automation System입니다. 기획서 기준은 72시간인데 최장 40분입니다. 메모리 누수가 있으면 3일째에 죽습니다.

방송 제품에서 이건 환불 문제가 아니라 신뢰의 문제입니다. 한 번 밤새 멈추면 그 고객은 다시 켜지 않습니다.

조치 — 72시간 연속 운전을 지금 걸어둔다. 결과가 나빠도 일찍 아는 편이 낫고, 그 사이 다른 항목을 붙일 수 있다. 협상 대상이 아니다.
03

편성 데이터에 백업도 마이그레이션도 없습니다

치명
server/store.js — schemaVersion · migrate · backup : 0곳

모든 편성이 data/db.json 파일 하나에 들어 있습니다. 깨지면 고객의 편성이 전부 사라집니다.

스키마 버전도 없어서 다음 버전에서 구조를 바꾸면 기존 고객의 데이터를 읽지 못합니다. 업데이트가 곧 데이터 손실이 됩니다.

조치 — 스키마 버전 도입, 기동 시 자동 백업(세대 보관), 버전 간 마이그레이션 경로.
04

로그가 남지 않아 지원이 불가능합니다

높음
server/index.js — 파일 기록(writeFile · appendFile) : 0곳

전환 계측과 힙 추이가 전부 메모리에 있어 프로세스가 죽으면 같이 사라집니다. 고객이 “어젯밤에 화면이 검게 나갔다”고 하면 확인할 방법이 없습니다.

역설적으로, 이 프로젝트에서 찾은 버그 대부분이 계측 덕분이었습니다. 그 계측이 고객 현장에서는 남지 않습니다.

조치 — 재생 이력·전환 계측·오류를 파일로 회전 기록. 고객이 한 번에 보낼 수 있는 진단 묶음 내보내기. 앱에 버전·빌드 표시.
05

설치·서명·자동 업데이트가 없습니다

높음
package.json — build 설정 없음 · devDeps: electron 뿐

지금은 npm install && npm run app입니다. 고객에게 Node.js 설치를 요구할 수 없습니다. 서명·공증이 없으면 macOS는 실행을 막고, Windows는 경고를 띄웁니다.

CMS가 이미 풀어둔 문제

CDMB CMS에 electron-builder · @electron/notarize · mac/win/dmg/nsis 설정 · 자동 업데이트가 모두 있습니다. 설정을 그대로 가져오면 됩니다. 필요한 것은 Apple Developer 계정과 인증서입니다.

조치 — CMS 빌드 설정 이식, 서명·공증 파이프라인, 자동 업데이트 채널.

약속과 실물이 다른 곳

기획서에 6종 소스라고 적혀 있지만 유튜브 어댑터가 없습니다. 제품 설명에 6종이라 쓸 수 없습니다. 둘 중 하나를 골라야 합니다.

  • 4종으로 줄여 말한다 — 로컬·폴더·Cloudflare·Bunny. 정직하고 즉시 가능
  • 만든다 — 다만 유튜브 임베드는 재생 품질을 통제할 수 없어 무결절이 최선 노력에 그칩니다. “6종 지원”이라 적고 한 종만 품질이 다르면 그것도 문제입니다
권장

1차 출시는 4종으로 정직하게 내고, 유튜브는 “아카이브 탐색용”으로 별도 표기해 기대치를 맞추는 편이 낫다고 봅니다. 온에어 품질이 중요한 콘텐츠는 Cloudflare·Bunny 미러링을 권하는 것이 이미 제품의 설계 방향이기도 합니다.

제품 UI가 아직 검증 하네스입니다

지금 관리 화면은 3단 컬럼에 전환 계측 표가 붙은 개발자용 도구입니다. 목업이 보여준 제품 UI와 다릅니다. 고객이 매일 보는 화면이므로 여기가 곧 제품 인상입니다.

없는 것왜 필요한가
운영 콘솔 온에어 감시와 즉시 개입. 방송 중 손을 댈 수 있는 유일한 창구
재생 이력 무엇이 언제 나갔는지. 광고 계약이 있으면 정산 근거가 된다
설정 화면지금은 소스 연결만 있다. 로고·오디오·기본값이 흩어져 있음
빈 상태 안내처음 켠 사람이 무엇부터 할지 알 수 없다
사람이 읽는 오류지금 오류는 개발자에게 하는 말이다

HC LIVE의 자리

“OBS를 이미 쓰는 사람이 편성만 자동화하고 싶을 때.” OBS를 대체하지 않고 공급하는 구조가 오히려 강점입니다 — 기존 워크플로를 바꾸지 않아도 됩니다.

  • 클라우드 소스를 처음부터 다룬다 — 대부분의 플레이아웃 도구는 로컬 파일을 전제한다
  • 규칙 빌더가 없다 — 블록 놓고 자동 채움 누르면 끝
  • 한국어 · 국내 지원
그래서 앞의 다섯 구멍이 더 중요합니다

무료 대안이 존재하는 시장입니다. 여기서 돈을 받는 근거는 기능 개수가 아니라 “설치하면 바로 되고, 밤새 안 죽고, 문제 생기면 물어볼 곳이 있다”입니다. 그 셋이 정확히 ①③④⑤입니다. 구멍을 막는 일이 곧 제품을 만드는 일입니다.

단계별 계획

작업량은 절대 기간 대신 상대 크기로 적습니다. 무엇이 크기를 좌우하는지를 함께 적었습니다.

A

팔 수 있는 최소

고객 환경에서 무너지지 않게 만드는 단계. 가장 지루하고 가장 중요합니다.

  • 72시간 연속 운전 통과 — 걸어두고 기다리는 시간이 대부분
  • ffmpeg 번들 — 개발은 작고, LGPL 확인이 크다
  • 로그 영속화 + 진단 내보내기 — 중간
  • 데이터 백업 · 스키마 버전 · 마이그레이션 — 중간
B

설치되고 갱신되는 것

CMS 자산을 재사용합니다. 계정·인증서 준비가 실제 병목입니다.

  • electron-builder 이식, 서명 · 공증 (Apple Developer 계정 필요)
  • 자동 업데이트 채널
  • 라이선스 활성화 — 오프라인 유예 필수. 방송 기계는 망 밖에 있을 수 있다
C

고객이 매일 보는 화면

설계와 목업이 이미 있어 새로 정할 것은 적습니다.

  • 운영 콘솔 — 온에어 감시 · 즉시 전환 · 스킵
  • 재생 이력 — 기록 · 조회 · 내보내기
  • 설정 화면 정리, 빈 상태 안내, 오류 문구 다시 쓰기
D

약속한 것 채우기

사람·하드웨어가 있어야 끝나는 항목이 섞여 있습니다.

  • 모니터 직출력 실검증 외부 모니터 필요
  • OBS 캡처 픽셀 확인 사람이 미리보기 확인
  • 유튜브 어댑터 — 또는 “4종”으로 문구 확정
E

차별화

1차 출시 이후. 없어도 팔 수 있는 것들입니다.

  • NDI 출력 — 화면 공간이 부족해질 때
  • OBS · vMix 연동 (씬 자동 전환) — obs-websocket 연결은 이미 확인됨
  • 자체 전송 스택 — 필요해질 때. 검토는 기획서 부록 C에 있음

먼저 정해야 할 사업 결정

기술 판단이 아니라 사업 판단이라 제가 정할 수 없는 것들입니다.

질문왜 지금 정해야 하나
누구에게 파는가 교회 미디어팀 · 1인 채널 운영자 · 행사 업체는 필요한 기능이 다르다. 운영 콘솔의 복잡도가 여기서 갈린다
가격 모델 영구 라이선스인지 구독인지에 따라 자동 업데이트·활성화 구조가 달라진다
과금 단위 기기당인지 채널당인지. 채널당이면 채널 수 제한을 앱이 강제해야 한다
지원 범위 원격 지원을 약속하면 진단·로그 요구 수준이 크게 올라간다
4K 정책 현재 보류. “1080p 전용”을 제품 사양에 명시할지 결정해야 한다

제안

72시간 연속 운전을 지금 겁니다. 3일 뒤에 답이 나오고, 그 사이 ffmpeg 번들 · 로그 영속화 · 데이터 백업을 붙일 수 있습니다. 결과가 나빠도 일찍 아는 것이 낫습니다 — 출시 직전에 알면 일정 전체가 흔들립니다.

기능을 더 만들고 싶은 유혹이 크겠지만, 방송 제품에서 팔리는 것은 기능이 아니라 밤새 안 죽는다는 믿음입니다.
